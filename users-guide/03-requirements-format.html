3. 管理データの書式

管理データは人が読むドキュメントですが、scripts/verify.py が機械的に検査できるフォーマットで書きます。通常は rd-author・test-designer・implementer が書くので、利用者が手で書く必要はありません。このページは、手で修正するときや、既存のドキュメントを移行するときのリファレンスです。

3.1 要求定義書（docs/requirements-definition.md）

節の構成

雛形（インストール時に作成）の節は次のとおりです。

文書情報・変更履歴 / 概要（目的 G-001）/ 対象と対象外 / 前提・制約（既定制約、PARAM、用語、状態）/ ペルソナ / 利用シナリオ / 要求 / ワークスペースとペルソナ別の情報表現 / 外部連携とマスター・ID / 決定記録 / 仮定・未解決事項（質問票、承認依頼、ASSUMPTION・TBD・競合、監査指摘、提案・仮説）/ 出典台帳（SRC-001）

要求が 150 件・300KB・業務境界 3 つを超えたら、要求定義書をインデックスにして、境界ごとのファイル docs/requirements/<境界名>.md に分割します。verify は両方を読みます。

1 要求 1 見出しと構造化欄（ルール B）

#### FR-012 入力の中断と再開
- 要求: 申請を入力している利用者は、入力を中断して後で再開したときに、入力済みの内容と未完了の項目を確認できる。
- 決定状態: 承認済み（依頼 2026-10-08）　出自: 依頼原文　優先度: MUST（中断のたびの再入力が離脱の原因）
- 上位: G-002　出典: SRC-003 §2.1
- 対象エンティティ: 申請　関係する状態: 下書き→提出済み　参照パラメータ: PARAM-004
- 関連する既存資産: 共通部品「下書き保存」
- 受入基準 AC-031: 入力途中で画面を閉じた利用者が、同じアカウントで再び開いたとき、入力済みの値が失われず、未完了の項目が識別できる。保持期間は {PARAM-004} とする。
  - 検証レベル: system
- 受入基準 AC-032: 保持期間を過ぎた下書きは一覧に表示されない。
  - 検証レベル: integration
  - BLOCKED: Q-007（保持期間の起点が TBD）
欄 必須 書き方
見出し ○ #### <要求 ID> <短いタイトル>。機能要求は FR-001、非機能要求は NFR-<区分>-001（区分: PERF、SEC、OPS、A11Y、UX など）
要求 ○ 「［対象者/システム］は、［状況・条件］に、［結果］を満たす。」の形で、1 要求に 1 つの主題だけを書く
決定状態 ○ 承認済み（依頼 YYYY-MM-DD）、承認済み（Q-### YYYY-MM-DD）、承認済み（承認依頼 YYYY-MM-DD）、承認済み（包括承認 YYYY-MM-DD・approval_policy）、AI提案／承認待ち、保留、却下、廃止（依頼 YYYY-MM-DD） のいずれか
出自 ○ 依頼原文／利用者決定／AI提案
優先度 ○ MUST／SHOULD／MAY と、その理由
上位 ○ G-001 などの目的、または「既定制約」
出典 SRC-xxx §…（出典台帳に定義した ID。CHK-24）または「依頼原文」など
対象エンティティ・関係する状態・参照パラメータ ○ 値がなければ「なし」。対象エンティティは用語の表か状態の表に、関係する状態はそのエンティティの状態の表に定義したものだけを書きます。参照パラメータには、本文・受入基準で {PARAM-xxx} として使う PARAM をすべて書きます（CHK-25）。監査時のクラスタリング（同じ対象・状態・PARAM を持つ要求どうしを突き合わせる）と影響分析に使います
関連する既存資産 共通部品「…」・API「…」・テーブル「…」 の形で書くと、カタログの該当する表に実在することを検査します（CHK-27）
エンティティの使い方 省略できます。注文（作成）、顧客（参照/更新） の形で、エンティティごとに 作成・参照・更新・削除 のいずれかを書きます。定義のないエンティティ・上記以外の語は CHK-25 のエラーです（scripts/entities.py list の「使い方」になります）
利用シナリオ 省略できます。1、2 の形で、第 5 節の番号付きの項目の番号を書きます。存在しない番号は CHK-25 のエラーです
エンティティの関係 省略できます。注文→商品（参照）、注文→顧客（外部キー） の形で、エンティティ間の関係と種別（参照・外部キー）を書きます。定義のないエンティティ・種別の語がないもの・上記以外の語は CHK-25 のエラーです。列の外部キーが別のエンティティの列を指すときは、同じ組の関係が自動で導出されます（重複は 1 件に統合）
列（カタログの任意の節） 省略できます。カタログ（docs/catalog.md）のテーブルの表に載っているテーブルごとに、見出し ### 列: <テーブル名>、対象エンティティ: 注文（1 つのエンティティに紐づくテーブルは省略可）、表 \| 列名 \| 型 \| キー \| 参照先 \| 説明 \| を書きます。キーは 主キー／外部キー／なし、参照先は 顧客.id（エンティティ.列）です。語の誤り・存在しない参照先・テーブルの表にないテーブルは CHK-25 のエラー（位置つき）です。列がないエンティティは「列未記載」と表示され、値は推測しません。リポジトリに DDL（*.sql の CREATE TABLE）や JSON Schema（*.schema.json、schema(s)/ 内の *.json）があれば、列・型・キー・外部キーを読み取り専用で補完します（管理データの値が優先され、食い違いは示されます。外部通信・書き換えはしません）
受入基準 MUST は ○ 受入基準 AC-xxx: <観察できる結果と判定条件>。その下に 検証レベル を書く
検証レベル 承認済みは ○ system（System Test の台帳と対応）、integration、unit、manual（docs/manual-tests.md で確認）
BLOCKED 該当時 ブロックの原因（未回答の Q-xxx、TBD、競合）を書きます

1 行に複数の欄を書くときは、全角スペース（）で区切ります。

PARAM・用語・質問票

| ID | 名前 | 値 | 単位 | 根拠 | 決定状態 |
|---|---|---|---|---|---|
| PARAM-004 | 下書きの保持期間 | 30 | 日 | 依頼原文 | 承認済み |

| 用語 | 定義 | 禁止同義語 |
|---|---|---|
| 申請 | 利用者が提出する書類 | 申込、エントリー |

| 対象エンティティ | 状態 | 遷移の条件 |
|---|---|---|
| 申請 | 下書き | 入力を始めたとき |
| 申請 | 提出済み | 提出ボタンを押したとき |

| ID | 重要度 | 質問 | 選択肢 | 推奨 | 状態 | 回答 |
|---|---|---|---|---|---|---|
| Q-007 | 高 | 保持期間の起点は | A: 作成時 / B: 最終更新時 | B | 未回答 | |
  • 閾値・期間・件数は本文にハードコードせず、PARAM を {PARAM-004} の形で参照します（CHK-14）。値が未定なら TBD（Q-007） と書きます。
  • 禁止同義語を使うと、CHK-15 が警告します。
  • 質問票の「状態」を「回答済み」にすると、その Q を参照している BLOCKED が CHK-18 でエラーになります（回答を反映して BLOCKED を外すきっかけになります）。

つながりの規則（体系としての一貫性）

要求定義書とカタログは、ばらばらの文書ではなく、ID と名前でつながった 1 つのデータとして扱います。verify は次のつながりを双方向に検査します。

つながり 規則 検査
目的 → 要求 → 受入基準 要求は上位の G を、受入基準は要求を持つ。承認済みの要求を持たない G は警告 CHK-03・04
受入基準 ⇔ System Test の台帳 ⇔ テスト system の AC と台帳のケースが 1:1。実装済みの MUST の ID がテストにある CHK-09・10・11
要求 → 用語・状態・PARAM・出典 構造化欄が定義を指す。どこからも使われない定義は警告 CHK-16・24・25・26
要求 ⇔ カタログ 承認済み・承認待ち・保留の要求は機能の表に 1 行。決定状態・題名が一致 CHK-07
カタログの表どうし 機能の表の「使っている共通部品」と共通部品の表の「使っている要求 ID」が一致。API・テーブル・共通部品の表の要求 ID が実在 CHK-24・27
すべての ID 本文・表・カタログに書いた ID は定義されている（参照先のないリンクを作らない） CHK-19・24

つながりは python scripts/rdcheck.py trace FR-012（要求の上流の G・出典、横の用語・状態・PARAM、下流の AC・台帳のケース・カタログ・コード）、trace G-002、trace 申請、trace PARAM-004、trace 下書き保存 で確認できます。要求を変えるときの影響範囲の確認に使います。

既定制約（ui_policy）

元になった Prompt が常に求める UI の方針（利用者がレイアウトを変更できる UI、ペルソナ別の情報表現）を「既定制約」の節に書きます。画面を持たないアプリ（バッチ・API のみ）は、前提・制約にその事実と根拠を「画面を持たない」と書けば省略できます（CHK-20）。

3.2 カタログ（docs/catalog.md）

4 つの表で構成します。1 行に 1 項目を書き、詳細はリンク先に任せます。

## 機能
| 要求 ID | 題名 | 決定状態 | 実装ファイル | テスト | 使っている共通部品 |
|---|---|---|---|---|---|
| FR-012 | 入力の中断と再開 | 承認済み | src/drafts/service.ts | tests/unit/drafts.test.ts | 下書き保存 |
| FR-013 | 申請の取消 | 承認済み | 未実装 | 未実装 | なし |

## API・イベント
| 名前 | 定義ファイル | 関連する要求 ID |
## テーブル
| テーブル名 | 定義ファイル | 正本のシステム | 関連する要求 ID |
## 共通部品
| 部品名 | ファイル | 用途 | 使っている要求 ID |
  • 決定状態・題名は要求定義書と一致させ、承認済み・承認待ち・保留の要求はすべて機能の表に 1 行ずつ載せます（CHK-07）。ファイルの列に書いたパスは実在している必要があります（CHK-08）。
  • 機能の表の「使っている共通部品」に書いた部品は共通部品の表に載せ、共通部品の表の「使っている要求 ID」は機能の表と一致させます（CHK-27。rdfix.py --only catalog --apply で機能の表に合わせられます）。API・テーブル・共通部品の表の「関連する要求 ID」は要求定義書に実在する ID にします（CHK-24）。
  • 未実装の要求は「未実装」と書きます。実装済みの MUST 要求の ID は、テストコード（テスト名か直前のコメント）か docs/manual-tests.md に出現している必要があります（CHK-09）。

3.3 ID 台帳（docs/id-registry.md）

行を追加できるのは scripts/next-id.py だけです。手で編集すると hook が拒否します（G-3）。

状態 意味
採番済み 採番したが、まだ本文にない
使用中 本文にある
廃止 本文に「廃止」として残っている
削除済み 本文から外した。再利用禁止（CHK-02）
欠番 採番したが使わなかった。再利用禁止

並行するブランチが同時に行を追加してもコンフリクトしないように、.gitattributes で merge=union を指定しています。worktree をまたいだ採番は、git の共通ディレクトリにある ebak-id-alloc.json で排他制御します。

3.4 System Test の台帳（tests/system/ledger.json）

{
  "version": 1,
  "ac_digests": { "AC-031": "sha256:3f6c0a1b2c3d4e5f" },
  "cases": [
    {
      "id": "E2E-001",
      "requirement_ids": ["FR-012"],
      "ac_ids": ["AC-031"],
      "title": "中断した入力を再開できる",
      "layer": "e2e",
      "command": "npx playwright test tests/system/e2e/fr-012.spec.ts",
      "canary": true,
      "status": "pass",
      "last_commit": "a1b2c3d",
      "last_run_at": "2026-10-08T10:15:00+09:00",
      "evidence": "work/runs/202610080900/logs/system-test/E2E-001-202610081015.log",
      "history": [{ "at": "…", "by": "test-designer", "change": "追加", "reason": "受入基準からケースを作成" }]
    }
  ]
}
キー 意味
id layer が e2e なら E2E-001、それ以外は IT-001。削除しても再利用しません
layer e2e、api、contract、data、nonfunctional、ai_eval
command リポジトリのルートから非対話で実行でき、成功時に exit 0 を返すコマンド
canary 最初に実行する主要フロー（スモークテスト）
status not_run、pass、fail、blocked（pass/fail は実際の実行結果でのみ設定される）
evidence 最後の実行のログ（/work の下。保持期間を過ぎると消えるので、必要なら再実行して作り直します）
ac_digests AC の本文（PARAM を展開したもの）のダイジェスト。AC が変更されると CHK-11 が検出します

「1:1」の定義: 承認済みで、BLOCKED でなく、検証レベルが system の AC と、台帳のケースが双方向に対応していて（1 つの AC に複数のケースがあってもよい）、ダイジェストが一致している状態を指します。

台帳は scripts/ledger.py 経由でだけ更新します（直接の編集は hook G-2 が拒否します）。ケースは削除できません。不要になったケースは ledger.py block --reason で blocked にし、理由を history に残します。

3.5 実行履歴（docs/run-history.md）

run-state.py finish が、1 run につき 1 行を追記します。列は run-id、開始、終了、HEAD、結果、実装した要求 ID、BLOCKED、AC pass 率、経過時間、1 回目のゲート通過率、AI クレジット、人の介入、検証済み要求です。run-id は一意である必要があります（CHK-23）。1.1.0 以前の表に追記するときは、「人の介入」と「検証済み要求」の列を自動で足し、過去の行には - を入れます。
