S8 データリファレンス（どの機能が、どのデータを読むか）

EABK Studio の各画面・機能が、どのファイルの、どの節・列・欄を読み、どう計算して表示するかの一覧です。数字や図の根拠を確かめたいとき（「この 62% は何の割合か」）に使います。 内容は実装（EABK-Studio/eabk_model.py、studio.py、web/js/*.js）から確認したものです。

  • 読むのはデータ層のファイルだけです。ソースコードの中身は開きません。カタログと台帳に書かれたパスの文字列を、名前として使うだけです（S8.1・S8.8）。
  • 通常の閲覧は読み取り専用です。書き込むのは、「整合性保守」で確認して実行したときの docs/catalog.md だけです（S8.9）。
  • 通信は 127.0.0.1 だけです（S8.10）。

S8.1 読むファイル

場所は、対象リポジトリの scripts/ebak.config.json（なければ scripts/hve.config.json）の management_files で変えられます。下は既定値です。

設定キー 既定のパス 読み方 使う画面
requirements docs/requirements-definition.md 見出し・箇条書き・表を解析 ほぼすべて
requirements_dir docs/requirements/*.md 同上（境界別に分けた要求ファイル。ファイル名の順） ほぼすべて
catalog docs/catalog.md 表を解析（機能・API・テーブル・共通部品） 2D/3D・配置・ソース対応・一貫性・保守
ledger tests/system/ledger.json JSON として解析 ダッシュボード・表（試験ケース）・一貫性・構造
id_registry docs/id-registry.md 表を解析（件数の集計と構造の判定） ダッシュボード・構造
run_history docs/run-history.md 表を解析 ダッシュボード・表（実行履歴）・構造
manual_tests docs/manual-tests.md 存在確認だけ（中身は解析しません） なし（--check の一覧と、モデルの meta.files のみ）
  • 起動時に、python EABK-Studio/studio.py --check で「どのファイルが見つかったか・何件解析できたか」を確認できます（04-troubleshooting.md）。
  • 要求は「docs/requirements-definition.md と docs/requirements/*.md」の両方から集めます。同じ ID が 2 つ以上あるときは、先のものを使い、重複として構造画面に出します。
  • ファイルがないときの見え方は S8.7 にあります。
  • コードの中身を読まない根拠: テスト test_nothing_outside_the_data_layer_is_read（EABK-Studio/tests/test_studio.py）が、src/ のファイルに書いた要求 ID が読まれないことを確認しています。

S8.2 要求定義書から取り出す項目

docs/requirements-definition.md と docs/requirements/*.md から、次の書式のものを取り出します（コードブロック内は無視）。書式は EABK 本体の管理データの書式に従います。

取り出すもの 書式 モデルの項目
要求 見出し ## 〜 ###### FR-nnn 題名、FR-<区分>、NFR-<区分>-nnn（太字も可） id・title・kind（FR/NFR）・cat（NFR の区分）
要求の本文 見出し直下の - 要求: …（次の項目が始まるまで続く行） text
決定状態 - 決定状態: 承認済み など。先頭の語で 承認済み / AI提案 / 保留 / 却下 / 廃止 に分類 status・statusKind
優先度 - 優先度: MUST など（MUST/SHOULD/MAY/COULD/WON'T を先頭から判定） priority
上位の目的 - 上位: G-001 goal
出自・出典 - 出自:・- 出典: origin・sources
扱うデータ - 対象エンティティ: 申請、承認 entities（, 、 ; ・ / で分割）
関係する状態・PARAM・既存資産 - 関係する状態:・- 参照パラメータ:・- 関連する既存資産: states・params・assets
エンティティ間の関係 - 関係: … relation（ER 図に使用）
受入基準 - AC-nnn: …、- 受入基準 AC-nnn: …、または見出し AC-nnn acs[].id・text
検証レベル AC の下の字下げ行 - 検証レベル: system acs[].level（先頭の語を小文字に）
BLOCKED AC の下の字下げ行 - BLOCKED: Q-003 … acs[].blocked、要求の blocked（Q-nnn を抽出）
索引表 見出し行に 要求ID・題名 と、所属ファイル か 優先度 を持つ表 見出しにない優先度・決定状態の補完。見出しのない要求の追加
目的 表（先頭列 ID が G-001。2〜4 列目が 題名・指標・方法）、または箇条書き - 目的 G-001: … goals
PARAM 表（ID=PARAM-001、列 名前・値・単位・根拠・決定状態） params
質問票 表（ID=Q-001、列 重要度・質問・選択肢・推奨・状態・回答） questions
出典の表 表（ID=SRC-001、列 資料・版・日付・区分） sources
監査指摘 表（ID=AUD-001、列 日付・カテゴリ・重大度・位置・要約・状態） audits
用語 表（先頭列 用語。1〜3 列目が 用語・定義・使ってはいけない言い方） terms
ペルソナ 表（先頭列 ペルソナ、列 業務・主要な判断・使うデータ・役割） personas
外部連携 表（先頭列 連携先。1〜5 列目が 連携先・方式・意味（方向）・正本・採番）、または箇条書き - 外部連携 名前: … integrations
決定記録 表（先頭列 日付、対象ID… 列を持つ。1〜5 列目が 日付・対象・決定・根拠・run） decisions
状態の表 表（見出しに 対象エンティティ と 状態。遷移… 列があれば遷移条件） stateMachines（状態と遷移。→ と ／ を解釈）
  • 受入基準の本文にある {PARAM-001} は、画面では置き換えず、本文のまま表示します（ただし S8.5.8 の AC digest の照合では PARAM の値に置き換えます）。
  • 利用シナリオ（利用シナリオ の見出しの下の箇条書き）は解析しますが、どの画面にも出しません。

S8.3 カタログから取り出す項目

docs/catalog.md の表を、見出し行の列名で見分けます。

表 見分ける列名 読む列 モデルの項目
機能 要求ID と 実装ファイル 要求ID・題名・決定状態・実装ファイル・テスト・使っている共通部品 catalog.features（impl・tests はパスらしい文字列だけ。なし・未実装・— などは空）
API・イベント 名前 と 定義ファイル 名前・定義ファイル・関連する要求（3 列目） catalog.apis
テーブル テーブル名 と 定義ファイル テーブル名・定義ファイル・正本のシステム・関連する要求ID catalog.tables
共通部品 部品名 部品名・ファイル・用途・使っている要求ID catalog.parts
  • 「パスらしい文字列」とは、/ を含むか、. と 1〜6 文字の拡張子で終わる文字列です。（…） の注記と :行番号 は取り除きます。ファイルが実在するかは確認しません。 カタログに書かれていれば「登録済み」です。
  • FR-nnn〜mmm、FR-nnn・mmm・kkk のような範囲・列挙は、定義済みの要求 ID に展開します。

S8.4 ほかのファイルから取り出す項目

ファイル 読む内容
tests/system/ledger.json cases[] の id・requirement_ids・ac_ids・title・layer・command・canary・status・last_commit・last_run_at・evidence、ac_digests。ケースの行番号は、ファイル内の "id" の位置から求めます
docs/id-registry.md 先頭の列が ID・種別・状態（または 使用状態）の表の全行
docs/run-history.md 先頭の列が run-id の表の全行（全列を文字列として保持）

command に書かれたパスは、テストファイルの名前として図に載せます（ファイルは開きません）。

用語（terms） 用語の表 用語・定義・使ってはいけない言い方
ペルソナ（personas） ペルソナの表 名前・業務・主要な判断・使うデータ・役割
外部連携（integrations） 外部連携の表 名前・方式・意味・正本
決定記録（decisions） 決定記録の表 日付・対象・決定・根拠・run
監査指摘（audits） 監査指摘の表 ID・日付・カテゴリ・重大度・位置・要約・状態
出典（sources） 出典の表 ID・資料・版・区分
実行履歴（runs） docs/run-history.md 表の先頭 8 列（列名はファイルのまま）

S8.5.8 構造（#/structure）

ナビゲーションには出ないページです（URL で開きます）。7 つのデータ層ごとに、現状（解析した件数）と理想（判定の基準）を比べ、1 レコードずつ判定した行を一覧にします。

層 読むデータ 主な判定（差分の種別）
要求定義書・境界別要求 要求・目的・AC 不足（決定状態・AC がない）、孤立（上位 の目的が存在しない）、参照不整合（AC 本文の ID が未定義）、重複（同じ要求 ID）、妥当
カタログ 機能の表 × 要求 余剰（要求にない行）、重複（同じ要求の行が複数）、参照不整合（決定状態が要求と違う）、妥当
System Test 台帳 × 要求・AC・PARAM 重複（ケース ID）、参照不整合（未定義の要求・AC、AC の親要求が不一致、AC 本文の digest が台帳の ac_digests と不一致）、妥当
ID 台帳 ID 台帳 × 要求・AC・目的 余剰（定義のない ID）、参照不整合（接頭辞と種別が不一致）、重複、妥当
実行履歴 run-history.md × 要求・ケース 参照不整合（存在しない要求・ケースを参照）、重複（run-id）、妥当
境界間 外部連携の表 不足（方式・方向・正本が空）、重複、妥当
  • 各行に 根拠（ファイル:行）が付きます。
  • AC の digest は、AC 本文の {PARAM-nnn} を値に置き換え、空白を詰めた文字列の SHA-256 先頭 16 桁です（sha256: 付き）。本文を変えたのに台帳を更新していないと「参照不整合」になります。
  • 内容の確かさ（意味の矛盾など）は判定しません。それは python scripts/verify.py と rd-auditor の役割です。

S8.5.9 一貫性（#/consistency）

ナビゲーションには出ないページです。要求 ID ごとに、5 つの層に記録があるかを調べます。

列 ○（✓）の条件
要求 要求定義書にその ID の要求がある
AC その要求に受入基準が 1 つ以上ある
試験 台帳のケースの requirement_ids にその ID がある（status は見ません）
カタログ カタログの機能の表にその ID の行がある
実装ファイル その行の 実装ファイル にパスが 1 つ以上ある

判定は、5 つともそろえば「正常」、1 つでも欠ければ「一層欠落」、カタログに行があるのに要求がなければ「参照先なし」です。

S8.5.10 整合性保守（#/maintenance）

表示 読むデータ 条件
保守候補 カタログの機能の行 × 要求 行の 題名 か 決定状態 が、要求正本（見出しの題名・決定状態）と文字列として異なる行。要求正本に存在しない行は「未対応」として表示

実行（書き込み）の条件は S8.9 です。

S8.5.12 実装状態（#/implstatus）

承認済みの要求が、実装の登録と試験の合否のどこにあるかを、状態別の積み上げ進捗バー（全体・目的別・優先度別）、かんばん、一覧表で表します。画面は管理データを読むだけで、対象リポジトリへは書き込みません。管理データが更新されると、再読込の後に状態と件数を再計算します。

読むデータ: 要求の 決定状態・AC の 検証レベル・BLOCKED、カタログの機能の表の 実装ファイル（パスが実在するもの）、台帳の cases[].requirement_ids と cases[].status。

状態 定義（上から順に判定）
未着手 カタログに行がない、または実装ファイル欄に実在するパスがない
実装登録済み・試験未登録 実装があり、検証レベル: system の AC を持つが、台帳にその要求のケースがない
実装登録済み・試験未合格 実装があり、台帳のケースに pass 以外（fail・blocked・not_run）が 1 件でもある
試験 pass 済み 実装があり、台帳のケースが 1 件以上あり、全件 pass
実装登録済み・system 試験対象外 実装があり、system の AC を持たず、台帳のケースもない
  • 決定状態が承認済みの要求だけが対象です。承認待ち・保留・却下・廃止の要求は分母に含めず、「対象外」の件数だけを別に示します。
  • 未回答の質問・TBD・競合で受入判定を進められない要求（BLOCKED を持つ AC がある要求）には、状態に加えて「停止中」の印（⏸）を付けます。
  • 状態は色だけでなく、記号（○ ◔ ✖ ✔ ◇）と状態名の語で区別します。かんばんのカードと表の行は、キーボード（Tab と Enter）で選べ、選ぶと詳細パネルが開いて他の表現と連動します。見出し・状態名・凡例は JA/EN の切替に従います。
  • ダッシュボードの「試験合格 %」との違い: 試験合格 % は台帳のケース単位（pass のケース ÷ ケースの数）です。実装状態は要求単位で、その要求に結び付くケースが 1 件でも pass 以外なら試験 pass 済みになりません。同じデータでも数字は一致しません。
  • 既存のノード属性 impl（done・none・unlisted）の意味は変わらず、2D/3D マップ・配置の表示も変わりません。実装状態は別の項目（implStatus）として計算します。

S8.7 欠けたときの見え方

欠けたもの 見え方
要求定義書も要求ファイルもカタログもない --check は終了コード 1。起動すると案内を出して終了。起動後に切り替えた場合も「データ層が見つかりません」で切り替わらない

S8.8 読まないもの

  • ソースコード・設定・ログ・work/ の中身（run の進捗・証跡・監査結果）。名前として出るのは、カタログと台帳に書かれたパスだけです。
  • docs/manual-tests.md の中身（存在確認だけ）。
  • .github/（エージェント・skill・hook）の中身。
  • 要求定義書の利用シナリオ（解析はするが表示しない）。

S8.9 書き込むもの

通常の閲覧・検索・CSV・リポジトリ切替では何も書きません。

書き込みは、整合性保守で 確認して実行 を押したときの docs/catalog.md だけです。選んだ要求の行の 題名 と 決定状態 の 2 つのセルを、要求正本に合わせます。

  1. プレビュー: 変更前後を表示し、トークンを発行します（ファイルは変えません）。
  2. 実行: ファイルの内容が、Studio の起動時（または前回の適用後）から変わっていないことを確認します。変わっていれば preview-conflict で止まります（別の手段でカタログを更新したあとは、Studio を起動し直してください）。
  3. 同じフォルダーに一時ファイル（.eabk-studio-*）を書いて置き換え、python scripts/verify.py --docs-only を実行します（scripts/verify.py がなければ読み取りの検査だけ）。
  4. 失敗（検査の失敗・書込みの失敗・対象外ファイルが同じ実体を指す）したら、元のバイト列と時刻・権限に戻してエラーを表示します。

S8.10 HTTP API（127.0.0.1 だけ）

メソッド・パス 内容
GET / ・ GET /<パス> EABK-Studio/web/ の静的ファイル（外のパスは 404）
GET /api/model 解析した全データ（JSON）。更新時刻の指紋が同じなら、キャッシュを返す
GET /api/fingerprint 管理データの更新の指紋（リポジトリのパス ＋ 各ファイルの更新時刻・サイズ）
GET /api/repo 現在の対象リポジトリのパス
POST /api/repo 対象リポジトリの切替（本文 {"path": …}）。X-EABK-Studio: 1 が必要
POST /api/maintenance/preview 本文 {"id": "<要求ID>"}。同じヘッダーが必要
POST /api/maintenance/apply 本文 {"token": …}。同じヘッダーが必要
  • 待ち受けは 127.0.0.1（既定のポートは 8765。使用中なら次の番号を最大 20 まで試す）。Host ヘッダーが 127.0.0.1・localhost・::1 以外の要求は 403 で拒否します。
  • POST は、ヘッダー X-EABK-Studio: 1 がなければ 403 です（ほかのサイトからの送信を避けるため）。本文は 8 KB まで。
  • 外部のサーバーへは何も送りません（フォント・CDN・解析も使いません。3D 用の three.js は同梱）。
