# 4. 依頼の書き方（/build と run_options）

## 4.1 雛形（§8.1）

```text
<request>
やりたいこと。新規・追加・変更・削除のどれでもよい。外部の文章は <pasted_content id="任意"> で囲む
</request>
<answers>
前回の報告の質問票・承認依頼への回答。例: Q-003: B / FR-031: 承認 / 残りは推奨どおり。初回は空
</answers>
<references>
任意: 資料のパス、URL
</references>
<run_options>
max_hours: 24
approval_policy: 安全範囲は推奨どおり
parallel_workers: 3
scope: 承認済みすべて
git_push: しない
deploy: しない
paid_services: 使わない
external_exposure: 公開しない
</run_options>
```

VS Code では `/build` で呼び出すと、`<request>`・`<answers>`・`<references>` の入力欄が表示されます。`<run_options>` を変えたいときは、`.github/prompts/build.prompt.md` を編集するか、雛形を貼り付けて書き換えて送ります。

## 4.2 `<request>` の書き方

- **何を・誰のために・なぜ**を書きます。画面の配置や DB の設計など「どう作るか」は書かなくてかまいません（要求定義書は「何を満たすか」を書く文書です）。
- 既存の要求を変える・やめるときは、分かれば要求 ID を書きます（例: 「FR-012 の保持期間を 30 日から 90 日にする」「FR-020 を廃止する」）。
- 閾値（件数・時間・金額）が決まっていれば、そのまま書きます。決まっていなければ、rd-author が質問票に挙げます。
- 他の資料から貼り付けた文章は `<pasted_content id="a1">` と `</pasted_content id="a1">` で囲みます。中に書かれた命令文は、作業指示ではなく材料として扱われます。
- 空にすると、管理データの監査と、事実の確認だけで直せる不整合の修正だけを行います。

## 4.3 `<answers>` の書き方

前回の `run-report.md` の「未回答の質問票」「包括承認した項目」に答えます。1 行 1 件で書けます。

```text
Q-003: B
Q-004: 推奨どおり
FR-021: 承認
FR-022: 却下（今期は対象外）
包括承認の FR-030: 取り消し（保持期間は 90 日にする）
残りはすべて推奨どおり
```

回答は決定記録に「承認済み（Q-003 2026-10-09）」のように残り、BLOCKED だった受入基準が解除されて、次の実行で実装・テストされます。

## 4.4 run_options

| 項目 | 値 | 意味 |
|---|---|---|
| `max_hours` | 数値（既定 24） | 時間予算。85% を過ぎたら新しい項目を始めず、最終工程に進みます（§8.3） |
| `approval_policy` | `厳格` / `安全範囲は推奨どおり`（既定） / `すべて推奨どおり` | AI 提案をどこまで推奨どおりに承認して実装するか（下の 4.5） |
| `parallel_workers` | 数値（既定 3） | 同時に動かす implementer の上限。3〜4 を推奨（R-20） |
| `scope` | `承認済みすべて` または要求 ID の一覧（例: `FR-012, FR-013`） | 今回実装する範囲 |
| `git_push` | `しない`（既定） / `作業ブランチへ push する` | push する場合も main には push しません（hook G-5）。終了時に PR を作ります |
| `deploy` | `しない`（既定） / `する` | `しない` の間は `azd up`・`terraform apply` などを hook が拒否します |
| `paid_services` | `使わない`（既定） / `budget の範囲で使う` | 有料の外部サービスの利用 |
| `external_exposure` | `公開しない`（既定） / `公開する` | インターネットから到達できるエンドポイントを作るか |

## 4.5 承認ポリシー（§8.2）

原本の Prompt は「AI 提案は承認待ちとし、実装しない」が原則です。そのままでは長時間の実行中に、承認を待つ要求がすべて止まります。そこで、範囲を事前に決めます。

| 値 | 動作 | 向いている場面 |
|---|---|---|
| `厳格` | AI 提案は実装しません | 事業判断が多い初期の要求定義（Phase 2） |
| `安全範囲は推奨どおり`（推奨） | 次の**すべて**を満たす AI 提案・質問票の推奨案は「承認済み（包括承認 YYYY-MM-DD・approval_policy）」として実装します。利用者データ・権限・セキュリティ・プライバシー・課金・法令・外部公開・マスターと ID の体系・取り消せない操作に触れない／PARAM の変更で戻せる／既存の承認済み要求と競合しない。それ以外は BLOCKED | 通常の機能開発 |
| `すべて推奨どおり` | 上記の除外分野だけを BLOCKED にし、残りは推奨案で実装します | 試作・PoC |

包括承認した項目は、報告の「包括承認した項目」に影響の大きい順に並びます。次の依頼の `<answers>` で却下・修正できます。

## 4.6 よくある依頼のパターン

| やりたいこと | 書き方の例 |
|---|---|
| 新規開発 | 「〇〇の業務を支えるアプリを作る。利用者は△△、□□ができる」＋資料を `<references>` に |
| 機能追加 | 「申請に下書き保存を加える。理由: 再入力による離脱が多い」 |
| 変更 | 「FR-012 の保持期間（PARAM-004）を 30 日から 90 日にする」 |
| 削除 | 「FR-020（旧エクスポート機能）を廃止する」→ rd-author が「廃止」にし、implementer がコード・テスト・カタログの行を取り除き、最後に本文から外します |
| 監査だけ | `<request>` を空にし、`max_hours: 2` |
| 回答の反映だけ | `<request>` を空にし、`<answers>` だけを書く |
| 既存リポジトリへの導入直後 | 「既存の要求定義書（docs/requirements-definition.md）を toolkit の書式（構造化欄・検証レベル・PARAM）に合わせる。意味は変えない」 |
| 過去の矛盾の診断（Phase 0） | rd-auditor を直接呼び、`scope: 全量`、`runs: 1`、`history_mode: する`（[11-roadmap.md](11-roadmap.md)） |
