# 11. 外部連携カタログ（`docs/integrations.md`）

アプリが API・ファイル・DB・イベントなどで行う、外部のアプリ・データとの連携を、1 連携 1 項目で記録するデータ層のファイルです（FR-1035〜FR-1037）。**任意**です。外部連携のあるアプリだけが作ります。ファイルがなければ、検査・Studio・清掃は従来どおり動き、エラーも警告も出ません。

## 11.1 インストールで受け取るもの

- `python tools/install.py` で、雛形 `docs/integrations.md`（書式の説明と空の索引表）が、**まだないときに限り**作られます。すでにある導入先のカタログは上書きされず、更新（再実行・`--force`）でも内容は変わりません。
- 検査は toolkit の `scripts/rdcheck.py`（CHK-28）と `scripts/next-id.py`（`INT` の採番）に入っていて、既存の配布と同じ手順（再実行）で更新されます。この章も `EABK-docs/` に配布されます。`--no-ci` の挙動（workflow を入れない）は変わりません。
- ファイル名は `scripts/ebak.config.json` の `management_files.integrations` で変えられます（既定は `docs/integrations.md`）。

## 11.2 書式

先頭に索引表（ID・名前・連携先・方向・状態・関連する要求）を置き、続けて 1 連携ごとに次の形で書きます。

```text
#### INT-001 受注 API
- 連携先: 取引先 A の受注システム
- 方向: 受信
- 方式: REST（HTTPS）
- データ分類: 取引データ（社外秘）
- 個人情報: あり
- 認証認可: OAuth 2.0 クライアントクレデンシャル
- 秘密の保管場所: Key Vault（名前だけを書く）
- 責任分界: 取引先 A は送信まで、当社は受信後の保管と処理
- 状態: 運用中
- 関連する要求: FR-012
- 頻度と量: TBD（Q-010）
- 可用性・SLA: なし
（以下、レート制限・エラー・再試行・冪等性・契約・バージョン・変更通知・監視・データ保持・障害時の代替・法務・ライセンスも、値・なし・TBD（Q-xxx）のどれかで書く）
```

- **必ず値を書く欄**（AC-208）: 連携先、方向（受信／送信／双方向）、方式、データ分類、個人情報、認証認可、責任分界、状態（検討中／運用中／廃止）、関連する要求（FR-xxx、NFR-xxx-xxx）。
- **そのほかの観点の欄**は、値、`なし`、`TBD（Q-xxx）`（質問票の ID）のどれかで必ず埋めます。欄が欠けていると検査が報告します。
- **認証情報の値は書きません**（AC-209）。トークン・パスワード・鍵・接続文字列の欄はありません。「認証認可」には方式の名前を、「秘密の保管場所」には保管場所の名前だけを書きます。値らしい文字列は検査が違反として報告します。

## 11.3 追加・変更・廃止の手順

追加・変更・廃止は **rd-author だけ**が行い、変更は要求定義書の変更履歴に記録します（手で書き換えません）。

1. **追加**: `python scripts/next-id.py INT` で `INT-xxx` を採番します（`--peek` なら記録しません）。見出し `#### INT-xxx <名前>` と欄を書き、索引表に 1 行足し、「関連する要求」に要求 ID を書きます。要求の側からは、本文や受入基準で `INT-xxx` を参照して対応づけます。値が未決の観点は `TBD（Q-xxx）` とし、質問票に Q を立てます。
2. **変更**: 欄の値を直します。状態は 検討中 → 運用中 → 廃止 の順に進めます。「運用中」にできるのは、関連する要求がすべて承認済みのときです（そうでないと警告）。
3. **廃止**: 状態を「廃止」にします。ID は再利用しません（ID 台帳で削除済み・欠番の ID を使うとエラー）。

## 11.4 検査（`python scripts/verify.py --docs-only`）

違反は ID と位置つきで報告され、exit 1 で終わります。違反がなければ exit 0 です。

| 違反 | 区分 |
|---|---|
| ID の重複、ID 形式の誤り（`INT-001` 形式でない） | error |
| 必須欄の欠落、16 観点の欄の欠落、空の欄 | error |
| 値が「値／なし／TBD（Q-xxx）」の形式でない、TBD の Q-ID が質問票にない | error |
| 方向・状態の値が定義外 | error |
| 関連する要求の ID が要求定義書にない、認証情報の値らしい文字列・欄 | error |
| 要求定義書が参照する `INT-xxx` がカタログにない（未定義参照） | error |
| 状態が「運用中」なのに、関連する要求がすべて承認済みではない、索引表と項目の不一致 | warn |

`python scripts/rdcheck.py trace INT-xxx` は、その連携を参照する要求と受入基準を一覧します。

## 11.5 外部連携の要求を書くとき（16 観点のチェックリスト）

外部連携を含む依頼では、rd-author と rd-auditor が `.github/skills/requirement-definition/integration-requirements.md` の 16 観点（確認する問い・要求に書く内容・受入基準の例・要求に書かない設計事項）を走査します。値が未決の観点は質問票（TBD の Q-ID）に回し、個人情報・認証認可・外部公開に触れる観点は包括承認の対象外です。要求のテンプレート（基本形と構造化欄・検証レベル付きの受入基準の例）も同じ文書にあります。
