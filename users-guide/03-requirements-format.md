# 6. 管理データの書式

管理データは人も読みますが、`scripts/verify.py` が機械的に検査できる形で書きます。通常は rd-author・test-designer・implementer が書くので、利用者が手で書く必要はありません。手で直すときや、既存の文書を移行するときの参照用です。

## 6.1 要求定義書（`docs/requirements-definition.md`）

### 節の構成

雛形（導入時に作成）の節: 文書情報・変更履歴 / 概要（目的 `G-001`）/ 対象と対象外 / 前提・制約（**既定制約**、**PARAM**、**用語**、状態）/ **ペルソナ** / 利用シナリオ / **要求** / ワークスペースとペルソナ別の情報表現 / 外部連携とマスター・ID / 決定記録 / 仮定・未解決事項（**質問票**、承認依頼、ASSUMPTION・TBD・競合、**監査指摘**、提案・仮説）/ 出典台帳（`SRC-001`）。

要求が 150 件・300KB・業務の境界 3 つを超えたら、要求定義書を索引にし、境界ごとのファイル `docs/requirements/<境界名>.md` に分けます。verify は両方を読みます。

### 1 要求 1 見出しと構造化欄（ルール B）

```markdown
#### FR-012 入力の中断と再開
- 要求: 申請を入力している利用者は、入力を中断して後で再開したときに、入力済みの内容と未完了の項目を確認できる。
- 決定状態: 承認済み（依頼 2026-10-08）　出自: 依頼原文　優先度: MUST（中断のたびの再入力が離脱の原因）
- 上位: G-002　出典: SRC-003 §2.1
- 対象エンティティ: 申請　関係する状態: 下書き→提出済み　参照パラメータ: PARAM-004
- 関連する既存資産: 共通部品「下書き保存」
- 受入基準 AC-031: 入力途中で画面を閉じた利用者が、同じアカウントで再び開いたとき、入力済みの値が失われず、未完了の項目が識別できる。保持期間は {PARAM-004} とする。
  - 検証レベル: system
- 受入基準 AC-032: 保持期間を過ぎた下書きは一覧に表示されない。
  - 検証レベル: integration
  - BLOCKED: Q-007（保持期間の起点が TBD）
```

| 欄 | 必須 | 書き方 |
|---|---|---|
| 見出し | ○ | `#### <要求 ID> <短い題名>`。機能要求は `FR-001`、非機能要求は `NFR-<区分>-001`（区分: PERF、SEC、OPS、A11Y、UX など） |
| 要求 | ○ | 「［対象者/システム］は、［状況・条件］に、［結果］を満たす。」1 要求 1 主題 |
| 決定状態 | ○ | `承認済み（依頼 YYYY-MM-DD）`、`承認済み（Q-### YYYY-MM-DD）`、`承認済み（承認依頼 YYYY-MM-DD）`、`承認済み（包括承認 YYYY-MM-DD・approval_policy）`、`AI提案／承認待ち`、`保留`、`却下`、`廃止（依頼 YYYY-MM-DD）` |
| 出自 | ○ | 依頼原文／利用者決定／AI提案 |
| 優先度 | ○ | MUST／SHOULD／MAY と理由 |
| 上位 | ○ | `G-001` などの目的、または「既定制約」 |
| 対象エンティティ・関係する状態・参照パラメータ | ○ | 値がなければ「なし」。監査のクラスタ化（同じ対象・状態・PARAM の要求を突き合わせる）に使います |
| 受入基準 | MUST は ○ | `受入基準 AC-xxx: <観察できる結果と判定条件>`。下に `検証レベル` |
| 検証レベル | 承認済みは ○ | `system`（System Test の台帳と対応）、`integration`、`unit`、`manual`（`docs/manual-tests.md` で確かめる） |
| BLOCKED | 該当時 | 依存先（未回答の `Q-xxx`、`TBD`、`競合`）を書きます |

1 行に複数の欄を書くときは**全角スペース**（`　`）で区切ります。

### PARAM・用語・質問票

```markdown
| ID | 名前 | 値 | 単位 | 根拠 | 決定状態 |
|---|---|---|---|---|---|
| PARAM-004 | 下書きの保持期間 | 30 | 日 | 依頼原文 | 承認済み |

| 用語 | 定義 | 禁止同義語 |
|---|---|---|
| 申請 | 利用者が提出する書類 | 申込、エントリー |

| ID | 重要度 | 質問 | 選択肢 | 推奨 | 状態 | 回答 |
|---|---|---|---|---|---|---|
| Q-007 | 高 | 保持期間の起点は | A: 作成時 / B: 最終更新時 | B | 未回答 | |
```

- 閾値・期間・件数は本文に直接書かず、PARAM を `{PARAM-004}` で参照します（CHK-14）。値が未定なら `TBD（Q-007）`。
- 禁止同義語を使うと CHK-15 が知らせます。
- 質問票の「状態」を「回答済み」にすると、その Q を参照する BLOCKED は CHK-18 でエラーになります（回答を反映して BLOCKED を外す合図）。

### 既定制約（ui_policy）

原本の Prompt が常に求める UI の方針（利用者がレイアウトを変更できる UI、ペルソナ別の情報表現）を「既定制約」の節に書きます。画面を持たないアプリ（バッチ・API のみ）は、その事実と根拠を前提・制約に「画面を持たない」と書けば省けます（CHK-20）。

## 6.2 カタログ（`docs/catalog.md`）

4 つの表です。1 行 1 項目。詳細はリンク先に任せます。

```markdown
## 機能
| 要求 ID | 題名 | 決定状態 | 実装ファイル | テスト | 使っている共通部品 |
|---|---|---|---|---|---|
| FR-012 | 入力の中断と再開 | 承認済み | src/drafts/service.ts | tests/unit/drafts.test.ts | 下書き保存 |
| FR-013 | 申請の取消 | 承認済み | 未実装 | 未実装 | なし |

## API・イベント
| 名前 | 定義ファイル | 関連する要求 ID |
## テーブル
| テーブル名 | 定義ファイル | 正本のシステム | 関連する要求 ID |
## 共通部品
| 部品名 | ファイル | 用途 | 使っている要求 ID |
```

- 決定状態は要求定義書と一致させます（CHK-07）。ファイルの列に書いたパスは実在が必要です（CHK-08）。
- 未実装の要求は「未実装」。実装済みの MUST の ID は、テストコード（テスト名か直前のコメント）か `docs/manual-tests.md` に現れる必要があります（CHK-09）。

## 6.3 ID 台帳（`docs/id-registry.md`）

`scripts/next-id.py` だけが行を追加します。手で編集すると hook が拒否します（G-3）。

| 状態 | 意味 |
|---|---|
| 採番済み | 採番したがまだ本文にない |
| 使用中 | 本文にある |
| 廃止 | 本文に「廃止」として残っている |
| 削除済み | 本文から外した。**再利用禁止**（CHK-02） |
| 欠番 | 採番したが使わなかった。再利用禁止 |

並行するブランチが同時に行を追加しても衝突しないよう、`.gitattributes` で `merge=union` にしています。worktree をまたいだ採番は、git の共通ディレクトリの `hve-id-alloc.json` で調停します。

## 6.4 System Test の台帳（`tests/system/ledger.json`）

```json
{
  "version": 1,
  "ac_digests": { "AC-031": "sha256:3f6c0a1b2c3d4e5f" },
  "cases": [
    {
      "id": "E2E-001",
      "requirement_ids": ["FR-012"],
      "ac_ids": ["AC-031"],
      "title": "中断した入力を再開できる",
      "layer": "e2e",
      "command": "npx playwright test tests/system/e2e/fr-012.spec.ts",
      "canary": true,
      "status": "pass",
      "last_commit": "a1b2c3d",
      "last_run_at": "2026-10-08T10:15:00+09:00",
      "evidence": "work/runs/202610080900/logs/system-test/E2E-001-202610081015.log",
      "history": [{ "at": "…", "by": "test-designer", "change": "追加", "reason": "受入基準からケースを作成" }]
    }
  ]
}
```

| 項目 | 意味 |
|---|---|
| `id` | `E2E-001`（layer が e2e）、それ以外は `IT-001`。削除しても再利用しません |
| `layer` | e2e、api、contract、data、nonfunctional、ai_eval |
| `command` | リポジトリのルートから非対話で実行でき、成功時に exit 0 を返すコマンド |
| `canary` | 先に実行する主要な流れ |
| `status` | not_run、pass、fail、blocked（pass/fail は実行結果でだけ付く） |
| `evidence` | 最後の実行のログ（`/work` の下。保持期間後は消えるので、必要なら再実行して作り直します） |
| `ac_digests` | AC の本文（PARAM を展開したもの）のダイジェスト。AC が変わると CHK-11 が知らせます |

**「1:1」の意味（A-3）**: 承認済み・BLOCKED でない・検証レベル system の AC と、台帳のケースが双方向に対応し（1 AC に複数ケースを許す）、ダイジェストが一致していること。

台帳は `scripts/ledger.py` でだけ更新します（直接の編集は hook G-2 が拒否）。ケースの削除はできません。止めるときは `ledger.py block --reason` で blocked にし、理由を history に残します。

## 6.5 実行履歴（`docs/run-history.md`）

`run-state.py finish` が 1 実行 1 行を追記します。列: run-id、開始、終了、HEAD、結果、実装した要求 ID、BLOCKED、AC pass 率、経過時間、1 回目のゲート通過率、AI クレジット。run-id は一意です（CHK-23）。
