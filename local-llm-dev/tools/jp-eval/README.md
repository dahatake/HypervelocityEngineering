# jp-eval: 日本語ローカル LLM 評価ツール

オフライン環境で使うローカル LLM が、**日本語のプロンプトにどれだけ従えるか**を客観的に測るツール。

[TUTORIAL.md 付録 A.6](../../TUTORIAL.md#a6-日本語タスクと指示追従率) の測定に使用したハーネスを、再利用可能な形に整理したもの。

---

## このツールが測るもの・測らないもの

| | 内容 |
|---|---|
| **測る** | 出力言語（日本語で回答したか）、形式遵守（コードフェンス・JSON スキーマ・見出し有無）、指定文字列の有無、簡体字の混入、生成速度（tok/s） |
| **測らない** | **意味的な正確さ、日本語としての自然さ、回答の有用性** |

> **重要**: 本ツールの数値が高いことは「日本語が上手い」ことを意味しない。**形式を守れるか**を測っているだけである。
> 意味的な品質は自動測定できないため、**実業務のプロンプトによる人手のブラインド評価が別途必要**である。

---

## 前提

- Python 3.10 以上（標準ライブラリのみ。追加パッケージ不要）
- OpenAI 互換ではなく **Ollama ネイティブ API**（`POST /api/chat`）を使う推論サーバ
  - 既定のエンドポイントは `http://127.0.0.1:11434`
- Foundry Local CLI 0.10.3 では `/api/chat` が 404 のため、そのままでは使えない（後述）

---

## 使い方

```powershell
# 1) 評価を実行する（結果は results/<model>.json に 1 件ずつ保存される）
python jp_eval.py run --models qwen3:8b phi4-mini:latest

# 2) 集計して Markdown を出力する
python jp_eval.py score
```

### 主なオプション

| オプション | 説明 |
|---|---|
| `--models` | 評価するモデル名（必須・複数可） |
| `--endpoint` | 推論サーバの URL（既定 `http://127.0.0.1:11434`） |
| `--suites` | `U1`（日本語タスク）/ `INSTR`（指示追従）を選択。既定は両方 |
| `--variants` | 指示追従の書き方。`negative`（否定形）/ `positive`（肯定形）。既定は両方 |
| `--out` | 結果 JSON の出力先ディレクトリ |
| `--num-ctx` | コンテキスト長（既定 8192） |
| `--retries` | 1 件あたりの再試行回数（既定 5） |

### 中断からの再開と再判定

`run` は **1 件ごとに結果を保存し、既に取得済みの設問はスキップする**。
推論サーバが落ちて途中で止まった場合は、**同じコマンドをもう一度実行するだけ**で未取得分だけが補完される。

> 実測では VRAM 8 GB の環境でモデルを連続切替すると推論サーバが異常終了することがあった
> （8 問中 4 問が欠測）。この再開機能はそのために用意している。

**判定は `score` 実行時に、保存された生出力（`final_answer`）から再計算される。**
このため判定ロジックの欠陥を修正した場合でも、**モデルを再実行せずに `score` をやり直すだけでよい**。
生出力が正本であり、合否判定はそこから導出される派生情報である。

## 評価スイート

### U1: 日本語タスク（8 問）

日本語仕様からのコード生成、バグ原因説明、JSON 構造化出力、技術用語説明、識別子命名、要約、エラー解析、否定指示追従。

> **U1-05 の注意**: 期待出力が「契約者番号 => contract_number」形式で**ひらがなを含まない**ため、
> ひらがな出現数による日本語判定が構造的に偽陰性になる。`score` は U1-05 の日本語判定を合格率から除外する。

### INSTR: 指示追従（10 問 × 2 通りの書き方）

同じ 4 ルールを **否定形**と**肯定形**で書き分けたシステムプロンプトを与え、追従率を比較する。

> **付録 A.6 の「74〜86%」とは別の測定である。**
> 付録の値は接頭辞ルールを含む **5 ルール**で測定したもので、本ツールの 4 ルールでは再現しない。

### バリアントの比較可能性を自動検査する

判定が特定の語の出現を見ているルール（「不明」と `python`）については、
**両バリアントがその語を指示しているか**を `run` の開始前に検査する。
片方だけが指示していないと、そのバリアントはモデルがどんなに忠実に従っても合格できず、
比較が無効になるためである（実際に初回測定でこの欠陥により誤った結論を出した）。
非対称を検出した場合は、長時間の測定を始める前に終了コード 2 で中断する。

### 指示文を変えたときの古い結果

各行には指示文の指紋（`variant_sha`）を保存している。

- `run`: 指示文が変わった行は**自動で破棄して取り直す**。
- `score`: 新旧が混ざっている場合は警告を出し、集計にも警告を埋め込む。

これにより、プロンプトを修正したのに古い測定値をそのまま使い続ける事故を防ぐ。

| # | 否定形 | 肯定形 | 判定方法 |
|---|---|---|---|
| r1 | 英語で回答してはならない | 回答は日本語で書く | ひらがな/カタカナが 5 文字以上 |
| r2 | Markdown の見出しを使ってはならない | 本文は段落と箇条書きだけで構成する | `^#{1,6}\s` に一致しない |
| r3 | 知らないことを推測で書いてはならない | 知らないことは「不明」と書く | 答えられない設問で「不明」を含む |
| r4 | コードをコードフェンスなしで書いてはならない | コードは ```` ```python ```` の中に書く | フェンスの言語が `python` |

r3 は `unknowable: true` の設問、r4 は `expects_code: true` の設問にのみ適用される（他は集計対象外）。

## 判定ロジックの既知の限界

初版の実装で以下の欠陥を作り込み、修正した。同種の誤りを繰り返さないため記録する。

1. **簡体字の誤検出**: 検出セットに「点」「会」「来」を含めていたが、これらは**正当な日本語漢字**であり、
   「問題点」のような正常な日本語が簡体字混入と誤判定された。現在は日本語で使わない字だけを列挙している
   （`SIMPLIFIED_ONLY`）。**セットを拡張する際は、その字が日本語の漢字表記として使われないことを必ず確認すること。**
2. **日本語判定の偽陰性**: ひらがな出現数を基準にしているため、**漢字と英数字だけで正しく構成された出力**は
   「日本語でない」と判定される。U1-05 のような設問では集計から除外する必要がある。
3. **見出し判定の偽陽性**: `^#{1,6}\s` で Markdown 見出しを検出していたため、**コードブロック内の
   Python コメント（`# こんな行`）を見出し違反と誤検出**していた。現在は `strip_code_blocks()` で
   コードブロックを除いてから判定する。
4. **推論トレースの残留**: `</think>` が欠けた打ち切り出力では推論トレースが除去されず、
   それを最終回答として判定していた。現在は未閉じの `<think>` 以降を切り落とす。

その他の限界:

- 設問数が U1 で 8 問と少なく、難易度も低いため**天井効果が起きやすい**。実測では 5 モデルすべてが 96〜100% となり差が出なかった。
  モデル選定の判断に使うなら、**自社の実プロンプトを `prompts.json` に追加して設問を増やすこと**。
- `temperature=0, seed=42` で固定しているが、**推論サーバやモデルの版が変われば結果は再現しない**。
- 判定は文字列マッチと正規表現であり、**意味を理解していない**。

---

## Foundry Local には非対応

本ツールは Ollama ネイティブの `POST /api/chat` 専用であり、Foundry Local には対応していない。
Foundry Local CLI 0.10.3 では、`POST /api/chat` は実測で 404、OpenAI 互換の
`POST /v1/chat/completions` は利用可能だった。Foundry Local 対応に変更する場合は次のいずれかが必要となる:

- `chat()` 関数を `/v1/chat/completions` 形式（`choices[0].message.content`）に書き換える
- OpenAI 互換 → Ollama 形式に変換するプロキシを挟む

なお Foundry Local のエンドポイントは**起動ごとにポートが変わる**ため、`foundry server status` で確認するか
`foundry server start --port <固定ポート> --idle-timeout 0` を使うこと。

## ファイル構成

| ファイル | 内容 |
|---|---|
| `jp_eval.py` | 実行・集計 CLI |
| `prompts.json` | 設問と判定条件の定義。**設問の追加はこのファイルだけを編集すればよい** |
| `test_jp_eval.py` | 判定ロジックの回帰テスト。`python test_jp_eval.py` で実行する |
| `results/` | 実行結果（モデルごとの JSON）。`run` が自動生成 |
| `summary.md` | `score` が出力する集計結果 |

## 判定ロジックを変更したら

判定は生出力から再計算されるため、モデルの再実行は不要。次の手順で反映する。

```powershell
python test_jp_eval.py   # 回帰テストが通ることを確認する
python jp_eval.py score  # 既存の結果を新しい判定で集計し直す
```

**判定ロジックを変更したら、対応するテストを `test_jp_eval.py` に必ず追加すること。**
上記「既知の限界」の 1〜4 は、いずれもテストがなかったために作り込まれた誤りである。
