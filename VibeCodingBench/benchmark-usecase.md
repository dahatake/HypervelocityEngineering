## 1. 文書の目的と適用範囲

### 1.1 目的

本書は、今後の Vibe Coding 実験で繰り返し使用する3つのアプリケーション課題の正本である。実装者（人またはAIエージェント）の選択、使用言語、フレームワーク、内部設計を比較対象から除外し、要求と観測方法を固定する。

比較する難易度は次の3段階とする。

| レベル | アプリケーション | 主な能力 |
|---|---|---|
| L1（初級） | 家計簿 CLI | CRUD、入力検証、集計、永続化、CLI UX |
| L2（中級） | 表計算エンジン | 2次元データ、式解析、依存関係、再計算、循環参照 |
| L3（上級） | SQL エンジン | 字句解析、構文解析、実行計画、型、NULL、集約、結合、エラー |

### 1.2 適用範囲

本書に含むものは、アプリケーションの外部仕様、受入基準、テストデータ、実験手順、測定指標、合否判定である。

本書に含めないものは、特定言語・ライブラリの指定、UIの見た目の細部、クラウドへのデプロイ、商用データベースとの完全互換、LLMの内部推論の評価である。

### 1.3 基準の扱い

- 本書の要求、受入基準、テストデータ、テストハーネスはベンチマーク運営者が管理する。
- 実装者は、要求定義書、公開テスト、実行方法を変更してはならない。
- 隠しテストは運営者だけが保持し、実装者には入力、期待値、テストIDを開示しない。
- 仕様とテストが矛盾する場合、実装者はテストに合わせて仕様を改変せず、`SPEC_CONFLICT` として報告する。
- 既定の完了判定はエージェントの報告ではなく、運営者の新しいプロセスで実行した検証スクリプトの終了コードと結果ファイルで行う。

## 2. 共通用語とID規約

### 2.1 用語

| 用語 | 定義 |
|---|---|
| 実装 | ベンチマーク開始後に作成または変更された本体コード、テスト、設定、文書 |
| 公開テスト | 実装者に提供するテスト。要求の代表例を含むが、全境界を含めない |
| 隠しテスト | 運営者だけが保持するテスト。合否の主判定に使用する |
| ケース | 1つの入力、操作列、期待結果、終了条件からなる検査単位 |
| 参照実装 | 仕様の意味を確認するための運営者用実装。提出物の正解コードではない |
| セッション | ベンチマーク開始から提出または時間上限到達までの連続したエージェント実行 |
| 正常終了 | 検証スクリプトがすべての必須ゲートを通過し、exit code 0を返す状態 |
| 部分完了 | 一部要求は満たすが、必須要求または必須テストが残る状態 |

### 2.2 ID規約

- 機能要求: `FR-<アプリ略称>-<3桁>`（例: `FR-BUD-001`）
- 非機能要求: `NFR-<分類>-<3桁>`（例: `NFR-REL-001`）
- 受入基準: `AC-<アプリ略称>-<3桁>`
- システムテスト: `E2E-<アプリ略称>-<3桁>`
- エラーコード: アプリごとに予約語を定義し、メッセージ本文ではなくコードを機械判定する

アプリ略称は、家計簿CLI=`BUD`、表計算エンジン=`SHT`、SQLエンジン=`SQL` とする。

## 3. 共通実行契約

### 3.1 実装成果物

提出物は次の構成を満たすこと。言語に応じて拡張子やビルド方式は変えてよい。

```text
/
  README.md
  LICENSE
  src/ または app/
  tests/
  scripts/verify.ps1 または scripts/verify.sh
  docs/requirements-definition.md
  docs/catalog.md
```

`README.md` には、依存関係の導入、ビルド、公開テスト、CLI/APIの起動、検証スクリプトの実行方法を記載する。

### 3.2 入出力の原則

- CLIを主インターフェースとする。GUI、Webサーバー、外部クラウドサービスは必須ではない。
- 標準入力、ファイル、標準出力、終了コードを利用できる。
- 成功時の機械可読出力はJSONまたはCSVを選択できるが、実装者は形式をREADMEで固定して説明する。
- エラー時は標準エラー出力へ診断情報を出し、標準出力に成功結果を混在させない。
- ロケール、タイムゾーン、浮動小数点丸めに依存しない。
- パスワード、秘密鍵、ネットワーク接続、外部APIを必要としない。

### 3.3 変更禁止対象

実装者は次を変更してはならない。

1. `benchmark/` または運営者が指定する隠しテスト
2. 隠しテストの探索、読み取り、無効化を行うコード
3. 期待値を入力やテスト名から推測して返すハードコード
4. `verify` の終了コードを常に0にする処理
5. 正常系の入力を受け付けるために、異常系の検証を無効化する処理

これらが検出された場合、機能テストの点数とは別にベンチマーク無効（`INVALID`）とする。

## 4. 共通非機能要求

### NFR-COR-001 再現性

同一OS、同一ランタイム、同一入力で、同一の結果と終了コードを返すこと。日時や乱数を使用する場合は固定値またはシード指定を可能にすること。

### NFR-COR-002 エラーの明確性

不正入力、未対応構文、参照エラー、I/Oエラーを区別できるエラーコードを返すこと。例外を握りつぶして成功扱いにしてはならない。

### NFR-COR-003 境界値

空入力、最小値、最大値、負数、ゼロ、長い文字列、重複、未知の名前を定義どおりに処理すること。

### NFR-COR-004 データ保全

保存操作に成功したデータは、再起動後に同じ意味で読み戻せること。部分書き込みによって既存データを破壊してはならない。

### NFR-COR-005 文書化

READMEに前提、制限、コマンド例、エラーの扱い、既知の未実装事項を記載すること。未実装を実装済みと記載してはならない。

### NFR-SEC-001 入力安全性

入力をコード、シェル、SQLとして再解釈してはならない。パス指定や式評価は許可された文法と範囲に制限すること。

### NFR-PERF-001 小規模性能

公開データセットを、運営者の標準環境で5秒以内に処理できること。起動時間を含むかどうかは各アプリの測定プロファイルに従う。

### NFR-PERF-002 大規模性能

隠しの性能ケースで、各アプリの上限時間を超えないこと。性能ケースの失敗は機能テストの合格とは別に記録する。

## 5. アプリケーション1: 家計簿 CLI（L1）

### 5.1 目的と利用者

個人が収入・支出を記録し、期間・カテゴリごとの残高を確認するローカルCLIである。利用者は端末からコマンドを入力し、データファイルを指定して操作する。

### 5.2 機能要求

#### FR-BUD-001 取引の登録

日付、金額、種別（`income` または `expense`）、カテゴリ、説明を持つ取引を1件登録できること。取引には再利用可能な一意IDを付与すること。

#### FR-BUD-002 取引の一覧

全取引または日付範囲・種別・カテゴリで絞り込み、日付順に一覧できること。同一日付では登録順またはID順を仕様として固定すること。

#### FR-BUD-003 取引の更新と削除

IDを指定して金額、日付、種別、カテゴリ、説明を更新できること。存在しないIDの更新・削除はエラーとし、他の取引を変更しないこと。

#### FR-BUD-004 集計

指定期間について、収入合計、支出合計、残高（収入−支出）を計算できること。カテゴリ別集計では、種別を混同しないこと。

#### FR-BUD-005 永続化

登録・更新・削除の結果をデータファイルへ保存し、別プロセスで再起動して読み戻せること。空の新規ファイルは初回操作時に作成できること。

#### FR-BUD-006 入力検証

不正な日付、ゼロ以下の金額、未定義の種別、空カテゴリ、過大な文字列、壊れたデータファイルを拒否すること。拒否時に既存データを失わないこと。

#### FR-BUD-007 出力形式

人間向け表示に加え、一覧と集計を機械可読形式で出力できること。機械可読形式では列名またはキー名を固定すること。

### 5.3 家計簿のデータ規則

- 日付はISO 8601の暦日 `YYYY-MM-DD` とする。
- 金額は通貨単位の整数（最小通貨単位）で保持し、浮動小数点誤差を発生させない。
- 金額の符号は種別で表し、`income` と `expense` の金額自体は正数とする。
- カテゴリと説明はUnicode文字列を許可するが、前後空白を正規化する。
- ファイル形式はJSON、CSV、SQLite等から選択できる。ただし、仕様上の意味は同じである。

### 5.4 家計簿の受入基準

| ID | Given | When | Then |
|---|---|---|---|
| AC-BUD-001 | 空のデータファイル | 収入1000を登録する | 1件が登録され、残高1000になる |
| AC-BUD-002 | 収入1000と支出250 | 全体を集計する | 収入1000、支出250、残高750になる |
| AC-BUD-003 | 2カテゴリの取引 | カテゴリ指定で一覧する | 指定カテゴリだけが返る |
| AC-BUD-004 | 既存ID | 金額を更新して再集計する | 更新後の金額だけが集計される |
| AC-BUD-005 | 既存ID | 削除して一覧する | 対象だけが消え、他は残る |
| AC-BUD-006 | 存在しないID | 更新または削除する | 明示的なnot-foundエラー、データ不変 |
| AC-BUD-007 | 不正日付または負金額 | 登録する | validationエラー、データ不変 |
| AC-BUD-008 | 保存済みデータ | 新しいプロセスで再読込する | 件数、値、順序の意味が維持される |
| AC-BUD-009 | 日本語カテゴリ・説明 | 登録、一覧、集計する | 文字化けや欠落がない |
| AC-BUD-010 | 壊れたデータファイル | 起動する | parseエラーを返し、成功結果を出さない |

### 5.5 家計簿のシステムテスト

最低限、`E2E-BUD-001`〜`E2E-BUD-010`を公開テストに、同等の境界変形・順序変形・大容量を隠しテストに含める。隠しテストの目安は74ケースとし、テスト数そのものではなく要求網羅率を管理する。

### 5.6 家計簿の性能プロファイル

- 小規模: 100件の登録・一覧・集計を5秒以内。
- 大規模: 10,000件を読み込み、期間集計を10秒以内。
- 目標要求文量の基準: 約4,458文字相当。ただし、実験時に本書を短縮・拡張した場合は実際の文字数を記録する。

## 6. アプリケーション2: 表計算エンジン（L2）

### 6.1 目的と利用者

小規模な表計算ファイルを読み込み、セルへの値・式の設定、再計算、参照、保存を行うエンジンである。GUIは不要であり、CLIまたはライブラリAPIで操作できること。

### 6.2 セルとシートの規則

- シート名とセルアドレスは大文字小文字を区別しない。
- セルアドレスは列名（`A`〜`ZZ`）と1始まりの行番号で表す。
- セルは空、数値、文字列、真偽値、エラー、式のいずれかを持つ。
- 未設定セルの値は空として扱う。
- 数値はIEEE 754倍精度または仕様に明記した同等精度で計算し、表示と内部値を混同しない。
- 式の区切り文字はカンマとする。

### 6.3 機能要求

#### FR-SHT-001 値の設定と取得

セルへ数値、文字列、真偽値を設定し、同じ値を取得できること。

#### FR-SHT-002 式の解析

`=A1+B1`、括弧、四則演算、単項符号を解析できること。演算子の優先順位は算術の一般的な規則に従うこと。

#### FR-SHT-003 セル参照と範囲

相対参照、絶対参照（`$A$1`）、矩形範囲（`A1:B3`）を扱えること。範囲を受ける関数は左上から右下の順で評価すること。

#### FR-SHT-004 組み込み関数

最低限 `SUM`、`AVERAGE`、`MIN`、`MAX`、`COUNT`、`IF` を実装すること。引数の型と空セルの扱いを関数ごとに一貫させること。

#### FR-SHT-005 再計算

参照元が変更されたとき、直接・間接に依存するセルを再計算すること。無関係なセルの値を変更してはならない。

#### FR-SHT-006 エラー伝播

未定義名、無効なアドレス、ゼロ除算、型不一致、関数引数不正を、区別可能なエラー値として返すこと。エラーを数値0として扱ってはならない。

#### FR-SHT-007 循環参照

直接または間接の循環参照を検出し、計算を無限に継続せず、循環エラーを返すこと。

#### FR-SHT-008 保存と読み込み

複数シート、値、式、エラー状態を保存し、再読込後も同じ計算結果になること。保存形式はJSON等から選択できる。

#### FR-SHT-009 一括入出力

CSVまたはJSONから表を読み込み、指定範囲を同形式で出力できること。行列の欠損を暗黙に別の値へ変換してはならない。

### 6.4 表計算の式文法

```text
formula  := "=" expression
expression := comparison
comparison := additive (("=" | "<>" | "<" | "<=" | ">" | ">=") additive)?
additive := multiplicative (("+" | "-") multiplicative)*
multiplicative := unary (("*" | "/") unary)*
unary := ("+" | "-")? primary
primary := number | string | boolean | cell_ref | range_ref
          | function_call | "(" expression ")"
function_call := name "(" argument_list? ")"
```

文字列リテラルは二重引用符、真偽値は `TRUE` / `FALSE` とする。文法外の入力はparseエラーとする。

### 6.5 表計算の受入基準

| ID | Given | When | Then |
|---|---|---|---|
| AC-SHT-001 | A1=2、B1=3 | C1に`=A1+B1`を設定する | C1は5 |
| AC-SHT-002 | A1=2、B1=3、C1=4 | `=A1+B1*C1`を評価する | 14（優先順位を保持） |
| AC-SHT-003 | A1:A3に1,2,3 | `=SUM(A1:A3)`を評価する | 6 |
| AC-SHT-004 | 数値と空セルを含む範囲 | `AVERAGE`と`COUNT`を評価する | 関数規則どおりに空セルを扱う |
| AC-SHT-005 | 式が参照するセル | 参照元を変更する | 依存セルが再計算される |
| AC-SHT-006 | `$A$1`を含む式 | 式を複製または再評価する | 絶対参照が移動しない |
| AC-SHT-007 | A1がB1、B1がA1を参照 | いずれかを取得する | 循環エラーで有限時間に終了 |
| AC-SHT-008 | `=1/0` | 評価する | ゼロ除算エラー、0ではない |
| AC-SHT-009 | 不正関数名・引数数 | 評価する | 明示的な関数エラー |
| AC-SHT-010 | 保存済み複数シート | 再読込して評価する | シートと式の意味が維持される |
| AC-SHT-011 | 日本語文字列 | 入出力する | Unicodeが保持される |
| AC-SHT-012 | 長い依存チェーン | 末端セルを取得する | 再帰深さや計算順序に依存せず正しい |

### 6.6 表計算のシステムテストと性能

- `E2E-SHT-001`〜`E2E-SHT-012`を公開テストの基礎とする。
- 隠しテストの目安は225ケースとし、演算子の組み合わせ、シート境界、型、循環、保存再読込、順序変形を含める。
- 小規模: 100×20セル、依存深さ20、5秒以内。
- 大規模: 1,000×100セル、依存深さ100、30秒以内。
- 目標要求文量の基準: 約9,908文字相当。

## 7. アプリケーション3: SQL エンジン（L3）

### 7.1 目的と利用者

ローカルのインメモリ表に対し、限定されたSQLを解析・実行する教育用SQLエンジンである。外部DBMSへクエリを委譲してはならない。

### 7.2 対象SQL

必須対応範囲は次のとおりとする。

```sql
CREATE TABLE table_name (column_name type [, ...]);
INSERT INTO table_name [(column [, ...])] VALUES (...)[, (...)];
SELECT [DISTINCT] select_item [, ...]
  FROM table_name [alias]
  [JOIN table_name [alias] ON predicate]
  [WHERE predicate]
  [GROUP BY column [, ...]]
  [HAVING predicate]
  [ORDER BY column [ASC|DESC] [, ...]]
  [LIMIT integer];
```

式は列参照、リテラル、`+ - * /`、比較、`AND OR NOT`、`IS NULL`、`IN`、`LIKE`、`CASE`、`COUNT`、`SUM`、`AVG`、`MIN`、`MAX` を含む。

### 7.3 機能要求

#### FR-SQL-001 字句解析

キーワード、識別子、数値、文字列、NULL、演算子、区切り文字を認識し、未知文字を明示的に拒否すること。キーワードの大文字小文字を区別しないこと。

#### FR-SQL-002 構文解析

対象SQLをASTまたは同等の構造へ変換すること。括弧、演算子優先順位、句の順序を正しく扱うこと。

#### FR-SQL-003 DDL

`CREATE TABLE`で列名と型を定義できること。同名テーブル、重複列、未知型を拒否すること。

#### FR-SQL-004 DML

`INSERT`で単一行・複数行を追加できること。列指定がある場合は指定順に対応付け、型不一致や列数不一致を拒否すること。

#### FR-SQL-005 基本SELECT

列選択、別名、`*`、定数式、空結果を処理できること。結果列名と列順を安定させること。

#### FR-SQL-006 WHEREと三値論理

`WHERE`、比較、`AND`、`OR`、`NOT`、`IS NULL`を実装すること。NULLとの比較はSQLの三値論理に従い、真だけを抽出すること。

#### FR-SQL-007 JOIN

内部等価結合を実装すること。結合列名が衝突する場合は修飾名または別名で解決できること。

#### FR-SQL-008 集約

`GROUP BY`、`HAVING`、集約関数、集約なしの全体集約を実装すること。空集合の集約結果を関数ごとに定義すること。

#### FR-SQL-009 ORDERとLIMIT

複数キーの昇順・降順、NULLの順序、LIMITを処理すること。同値行の順序は入力順を保持するか、安定した規則を文書化すること。

#### FR-SQL-010 エラー分類

字句、構文、名前解決、型、実行、制限超過を区別すること。エラー時に部分的な結果を成功として返してはならない。

#### FR-SQL-011 セキュリティ境界

対象外のDDL/DML、ファイルアクセス、シェル実行、外部ネットワーク、コメントによる文法回避を実行しないこと。

#### FR-SQL-012 実行結果形式

列名、行、型、エラーコードを機械可読形式で返すこと。結果の行順はORDER BYがある場合はその規則に従うこと。

### 7.4 SQLの型とNULL

- 必須型は `INTEGER`、`REAL`、`TEXT`、`BOOLEAN`、`DATE` とする。
- 型変換は暗黙に行わず、仕様上許可された比較・算術だけを実行する。
- `NULL = NULL`、`NULL <> value` はTRUEにしてはならない。
- `IS NULL` と `IS NOT NULL` はNULL判定の専用演算子とする。
- `COUNT(*)` は行数、`COUNT(column)` は非NULL値の数とする。
- `SUM`、`AVG`、`MIN`、`MAX`はNULLを除外し、対象が空の場合は仕様で定めたNULLを返す。

### 7.5 SQLの受入基準

| ID | Given | When | Then |
|---|---|---|---|
| AC-SQL-001 | employees表を作成 | CREATE TABLEを実行 | スキーマが登録される |
| AC-SQL-002 | 3行のデータ | SELECT列指定を実行 | 指定列・指定順の3行が返る |
| AC-SQL-003 | NULLを含む列 | `WHERE col = 1`を実行 | NULL行は抽出されない |
| AC-SQL-004 | NULLを含む列 | `WHERE col IS NULL`を実行 | NULL行だけが抽出される |
| AC-SQL-005 | 2表に共通キー | INNER JOINを実行 | 一致する組だけが返る |
| AC-SQL-006 | 部門別データ | GROUP BYとCOUNT/SUMを実行 | グループごとの集計が正しい |
| AC-SQL-007 | 集計結果 | HAVINGを実行 | 条件を満たすグループだけが返る |
| AC-SQL-008 | 複数の同値行 | ORDER BY複数キーを実行 | 各キーの優先順と方向が守られる |
| AC-SQL-009 | 10行以上 | LIMITを実行 | 指定件数以下で返る |
| AC-SQL-010 | 不正SQL | 実行 | 構文または字句エラーで終了 |
| AC-SQL-011 | 未知テーブル・列 | 実行 | 名前解決エラーで終了 |
| AC-SQL-012 | 列数・型不一致INSERT | 実行 | データを追加せずエラー |
| AC-SQL-013 | 対象外文 | 実行 | unsupportedエラー、外部操作なし |
| AC-SQL-014 | 同一SQLを3回 | 実行 | 結果とエラーコードが一致 |

### 7.6 SQLのシステムテストと性能

- `E2E-SQL-001`〜`E2E-SQL-014`を公開テストの基礎とする。
- 隠しテストの目安は564ケースとし、字句境界、構文の組み合わせ、NULL、型、結合、集約、順序、異常系、対象外操作を含める。
- 小規模: 5表、各100行、複合クエリを5秒以内。
- 大規模: 10表、各10,000行、JOIN・GROUP BYを60秒以内。
- 目標要求文量の基準: 約7,155文字相当。
- SQLは最も失敗しやすい上級課題であるため、単一プロンプトで完了しない場合の分割実行（lexer/parser、storage、executor、aggregation、test）を許可する。ただし、測定では分割有無を必ず記録する。

## 8. テスト設計要求

### 8.1 テスト階層

提出物には、可能な限り次の階層を含める。

1. 単体テスト: parser、validator、calculator等の小単位
2. 結合テスト: 永続化、依存解決、実行器等の組み合わせ
3. システムテスト: 利用者と同じCLI/API境界からのE2E
4. 隠しテスト: 公開されていない境界、組み合わせ、異常系

### 8.2 受入基準との追跡性

- 各テストは1つ以上のAC IDをコメントまたはメタデータで参照する。
- 各FRは少なくとも1つのACと1つのシステムテストを持つ。
- `docs/catalog.md`に `Requirement ID / AC ID / Test ID / Implementation reference` の対応を記録する。
- 対応がない要求、重複ID、存在しないIDは検証失敗とする。

### 8.3 テスト不正対策

- テストファイルを変更して合格させる提出物は無効とする。
- 実装コードからテスト期待値を読み出すテストは禁止する。
- 環境変数やカレントディレクトリだけで隠しテストを判定する実装は禁止する。
- テストが仕様と矛盾していると判断した場合は、テスト変更ではなく `SPEC_CONFLICT` を報告する。

## 9. ベンチマーク実行プロトコル

### 9.1 固定する条件

実験ごとに次を記録し、比較可能性を保つ。

| 区分 | 記録項目 |
|---|---|
| 環境 | OS、CPU、RAM、ランタイム、依存関係のバージョン |
| モデル | モデル名、推論設定、コンテキスト設定 |
| エージェント | VS Code/Copilot等のバージョン、Autopilot、サブエージェント有無 |
| 入力 | Prompt全文のハッシュ、要求定義書の版、添付資料 |
| 時間 | 開始、終了、実行時間、停止・再開・中断 |
| コスト | 入力/出力Token、cache、AIクレジット、Premium Request |
| 変更 | commit、変更ファイル、実装行数、テスト行数 |
| 結果 | verify終了コード、公開/隠しテスト、性能、INVALID判定 |

### 9.2 実行手順

1. 空のリポジトリに基準ファイルと公開テストだけを配置する。
2. 実行環境とGitの初期状態を記録する。
3. 事前に指定したPromptを入力し、途中の人手介入を記録する。
4. エージェントの「完了」報告では終了せず、運営者プロセスで `verify` を実行する。
5. 公開テスト、隠しテスト、性能測定、静的検査を独立して実行する。
6. `run-report.md`に結果を記録し、同じ条件で必要な再実行を行う。
7. 実験結果を本書の要求版と紐づける。

### 9.3 Promptの比較単位

最低限、次の比較を個別の実験として記録する。

- 単一エージェント、単一Prompt
- 要求を明示した単一エージェント
- 要求を機能単位に分割した連続Prompt
- サブエージェントを利用した実行
- 上級SQLのみ、実装領域を分割した実行

同一実験内でモデル、Prompt、要求版、公開テストを同時に変更してはならない。

## 10. 測定指標と合否

### 10.1 機能品質

| 指標 | 定義 |
|---|---|
| Hidden pass rate | 隠しテスト合格数 / 隠しテスト総数 |
| AC coverage | 合格したAC数 / AC総数 |
| FR completion | 満たした必須FR数 / 必須FR総数 |
| Error correctness | エラーケースで正しい分類・終了コードを返した割合 |
| Regression rate | 公開テストを壊した変更数 |

### 10.2 生産性

- wall-clock time: 最初のPromptから最終verifyまでの経過時間
- active execution time: エージェント・テスト・ビルドの実行時間
- human intervention count: 追加Prompt、手動修正、承認の回数
- Token: input、output、cache read、cache writeを分けた総量
- AI credit: 利用サービスで取得できるクレジットを原値で記録

### 10.3 必須合否条件

次のいずれかを満たさない提出物は、品質スコアが高くても `FAIL` とする。

1. ビルドまたは起動に失敗する。
2. 必須ACが1件でも未達である。
3. verifyがexit code 0を返さない。
4. 隠しテストで不正行為が検出される。
5. 既存データを破壊する、またはエラーを成功扱いする。
6. 仕様・テスト・結果の対応が追跡できない。

### 10.4 総合スコア

合否とは別に、次の重みで比較用スコアを算出する。

```text
quality = 0.60 * hidden_pass_rate
        + 0.20 * ac_coverage
        + 0.10 * error_correctness
        + 0.10 * regression_free_rate

productivity = normalized_quality / (wall_clock_minutes
                                    + token_millions * 0.1
                                    + human_intervention_count * 5)
```

`normalized_quality` は0〜1、時間とTokenの正規化方法は実験レポートで明記する。品質未達を生産性で相殺してはならない。

## 13. 変更管理と将来拡張

- 本書の要求IDは、一度公開した版では再利用しない。
- 要求を追加するときは、FR、AC、E2E、隠しテスト、catalog、READMEのすべてを更新する。
- 既存要求の意味を変更するときはメジャー版を上げ、旧版での結果と比較できるようにする。
- 新しいアプリを追加するときは、L1〜L3のいずれかの難易度、参照データ、公開・隠しテスト数、性能上限、完了条件を同じ形式で定義する。
- 外部サービス、デプロイ、GUI、生成AI機能を追加する場合は、別の実験プロファイルとして切り分け、ローカル基準の結果と混在させない。
