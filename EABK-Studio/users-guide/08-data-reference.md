# 8. データリファレンス（どの機能が、どのデータを読むか）

EABK Studio の各画面・機能が、**どのファイルの、どの節・列・欄を読み**、**どう計算して**表示するかの一覧です。数字や図の根拠を確かめたいとき（「この 62% は何の割合か」）に使います。
内容は実装（`EABK-Studio/eabk_model.py`、`studio.py`、`web/js/*.js`）から確認したものです。

- 読むのは**データ層のファイルだけ**です。ソースコードの中身は開きません。カタログと台帳に書かれた**パスの文字列**を、名前として使うだけです（8.1・8.8）。
- 通常の閲覧は読み取り専用です。書き込むのは、「整合性保守」で確認して実行したときの `docs/catalog.md` だけです（8.9）。
- 通信は `127.0.0.1` だけです（8.10）。

## 8.1 読むファイル

場所は、対象リポジトリの `scripts/ebak.config.json`（なければ `scripts/hve.config.json`）の `management_files` で変えられます。下は既定値です。

| 設定キー | 既定のパス | 読み方 | 使う画面 |
|---|---|---|---|
| `requirements` | `docs/requirements-definition.md` | 見出し・箇条書き・表を解析 | ほぼすべて |
| `requirements_dir` | `docs/requirements/*.md` | 同上（境界別に分けた要求ファイル。ファイル名の順） | ほぼすべて |
| `catalog` | `docs/catalog.md` | 表を解析（機能・API・テーブル・共通部品） | 2D/3D・配置・ソース対応・一貫性・保守 |
| `ledger` | `tests/system/ledger.json` | JSON として解析 | ダッシュボード・表（試験ケース）・一貫性・構造 |
| `id_registry` | `docs/id-registry.md` | 表を解析（件数の集計と構造の判定） | ダッシュボード・構造 |
| `run_history` | `docs/run-history.md` | 表を解析 | ダッシュボード・表（実行履歴）・構造 |
| `manual_tests` | `docs/manual-tests.md` | **存在確認だけ**（中身は解析しません） | なし（`--check` の一覧と、モデルの `meta.files` のみ） |

- 起動時に、`python EABK-Studio/studio.py --check` で「どのファイルが見つかったか・何件解析できたか」を確認できます（[04-troubleshooting.md](04-troubleshooting.md)）。
- 要求は「`docs/requirements-definition.md` と `docs/requirements/*.md`」の**両方**から集めます。同じ ID が 2 つ以上あるときは、先のものを使い、重複として構造画面に出します。
- ファイルがないときの見え方は 8.7 にあります。
- コードの中身を読まない根拠: テスト `test_nothing_outside_the_data_layer_is_read`（`EABK-Studio/tests/test_studio.py`）が、`src/` のファイルに書いた要求 ID が読まれないことを確認しています。

## 8.2 要求定義書から取り出す項目

`docs/requirements-definition.md` と `docs/requirements/*.md` から、次の書式のものを取り出します（コードブロック内は無視）。書式は EABK 本体の[管理データの書式](../../users-guide/03-requirements-format.md)に従います。

| 取り出すもの | 書式 | モデルの項目 |
|---|---|---|
| 要求 | 見出し `## 〜 ###### FR-nnn 題名`、`FR-<区分>`、`NFR-<区分>-nnn`（太字も可） | `id`・`title`・`kind`（FR/NFR）・`cat`（NFR の区分） |
| 要求の本文 | 見出し直下の `- 要求: …`（次の項目が始まるまで続く行） | `text` |
| 決定状態 | `- 決定状態: 承認済み` など。先頭の語で 承認済み / AI提案 / 保留 / 却下 / 廃止 に分類 | `status`・`statusKind` |
| 優先度 | `- 優先度: MUST` など（MUST/SHOULD/MAY/COULD/WON'T を先頭から判定） | `priority` |
| 上位の目的 | `- 上位: G-001` | `goal` |
| 出自・出典 | `- 出自:`・`- 出典:` | `origin`・`sources` |
| 扱うデータ | `- 対象エンティティ: 申請、承認` | `entities`（`,` `、` `;` `・` `/` で分割） |
| 関係する状態・PARAM・既存資産 | `- 関係する状態:`・`- 参照パラメータ:`・`- 関連する既存資産:` | `states`・`params`・`assets` |
| エンティティ間の関係 | `- 関係: …` | `relation`（ER 図に使用） |
| 受入基準 | `- AC-nnn: …`、`- 受入基準 AC-nnn: …`、または見出し `AC-nnn` | `acs[].id`・`text` |
| 検証レベル | AC の下の字下げ行 `- 検証レベル: system` | `acs[].level`（先頭の語を小文字に） |
| BLOCKED | AC の下の字下げ行 `- BLOCKED: Q-003 …` | `acs[].blocked`、要求の `blocked`（`Q-nnn` を抽出） |
| 索引表 | 見出し行に `要求ID`・`題名` と、`所属ファイル` か `優先度` を持つ表 | 見出しにない優先度・決定状態の補完。見出しのない要求の追加 |
| 目的 | 表（先頭列 `ID` が `G-001`。2〜4 列目が 題名・指標・方法）、または箇条書き `- 目的 G-001: …` | `goals` |
| PARAM | 表（`ID`=`PARAM-001`、列 名前・値・単位・根拠・決定状態） | `params` |
| 質問票 | 表（`ID`=`Q-001`、列 重要度・質問・選択肢・推奨・状態・回答） | `questions` |
| 出典の表 | 表（`ID`=`SRC-001`、列 資料・版・日付・区分） | `sources` |
| 監査指摘 | 表（`ID`=`AUD-001`、列 日付・カテゴリ・重大度・位置・要約・状態） | `audits` |
| 用語 | 表（先頭列 `用語`。1〜3 列目が 用語・定義・使ってはいけない言い方） | `terms` |
| ペルソナ | 表（先頭列 `ペルソナ`、列 業務・主要な判断・使うデータ・役割） | `personas` |
| 外部連携 | 表（先頭列 `連携先`。1〜5 列目が 連携先・方式・意味（方向）・正本・採番）、または箇条書き `- 外部連携 名前: …` | `integrations` |
| 決定記録 | 表（先頭列 `日付`、`対象ID…` 列を持つ。1〜5 列目が 日付・対象・決定・根拠・run） | `decisions` |
| 状態の表 | 表（見出しに `対象エンティティ` と `状態`。`遷移…` 列があれば遷移条件） | `stateMachines`（状態と遷移。`→` と `／` を解釈） |

- 受入基準の本文にある `{PARAM-001}` は、画面では置き換えず、本文のまま表示します（ただし 8.5.8 の AC digest の照合では PARAM の値に置き換えます）。
- 利用シナリオ（`利用シナリオ` の見出しの下の箇条書き）は解析しますが、**どの画面にも出しません**。

## 8.3 カタログから取り出す項目

`docs/catalog.md` の表を、**見出し行の列名**で見分けます。

| 表 | 見分ける列名 | 読む列 | モデルの項目 |
|---|---|---|---|
| 機能 | `要求ID` と `実装ファイル` | 要求ID・題名・決定状態・実装ファイル・テスト・使っている共通部品 | `catalog.features`（`impl`・`tests` はパスらしい文字列だけ。`なし`・`未実装`・`—` などは空） |
| API・イベント | `名前` と `定義ファイル` | 名前・定義ファイル・関連する要求（3 列目） | `catalog.apis` |
| テーブル | `テーブル名` と `定義ファイル` | テーブル名・定義ファイル・正本のシステム・関連する要求ID | `catalog.tables` |
| 共通部品 | `部品名` | 部品名・ファイル・用途・使っている要求ID | `catalog.parts` |

- 「パスらしい文字列」とは、`/` を含むか、`.` と 1〜6 文字の拡張子で終わる文字列です。`（…）` の注記と `:行番号` は取り除きます。**ファイルが実在するかは確認しません。** カタログに書かれていれば「登録済み」です。
- `FR-nnn〜mmm`、`FR-nnn・mmm・kkk` のような範囲・列挙は、定義済みの要求 ID に展開します。

## 8.4 ほかのファイルから取り出す項目

| ファイル | 読む内容 |
|---|---|
| `tests/system/ledger.json` | `cases[]` の `id`・`requirement_ids`・`ac_ids`・`title`・`layer`・`command`・`canary`・`status`・`last_commit`・`last_run_at`・`evidence`、`ac_digests`。ケースの行番号は、ファイル内の `"id"` の位置から求めます |
| `docs/id-registry.md` | 先頭の列が `ID`・`種別`・`状態`（または `使用状態`）の表の全行 |
| `docs/run-history.md` | 先頭の列が `run-id` の表の全行（全列を文字列として保持） |

`command` に書かれたパスは、テストファイルの**名前**として図に載せます（ファイルは開きません）。

## 8.5 画面ごとに、何を読むか

以降の表の「計算」は、画面に出る数字・図の求め方です。分母・分子を取り違えやすいものに注意してください。

### 8.5.1 ダッシュボード（`#/dashboard`）

| 表示 | 読むデータ | 計算 |
|---|---|---|
| 要求 | 要求定義書の要求 | 解析できた要求（FR・NFR）の数。**決定状態を問わず全件** |
| 承認済み % | 要求の `決定状態` | 先頭が「承認済み」の数 ÷ 要求の数（小数第 1 位まで） |
| 実装登録 % | 要求 × カタログの機能の表 | 「実装ファイル」にパスが 1 つ以上ある要求の数 ÷ **要求の数（全件）**。カタログに行がない要求・実装ファイルが空の要求は「未登録」。ファイルの実在は見ません |
| 受入基準 | 要求の AC | 全要求の AC の数 |
| 試験合格 % | 台帳の `cases[].status` | `status` が `pass` のケース ÷ ケースの数。`not_run` は合格に含めません |
| 未回答の質問 | 質問票の `状態` | 状態に「回答済み・解決済み・取り下げ・クローズ」を含まない質問の数 |
| BLOCKED の要求 | AC の `BLOCKED` | `Q-nnn` を含む BLOCKED を持つ AC がある要求の数 |
| ファイル / コンポーネント | カタログ・台帳 | 図に載ったファイルの数 / その最上位の部品の数（8.5.2） |
| 決定状態・優先度 | 要求 | それぞれの内訳（円グラフ。クリックで該当要求を 2D マップで強調） |
| 目的ごとの実装進捗 | 目的 × 要求 × カタログ | 目的（G）ごとに、その目的を `上位` に持つ要求のうち実装登録済みの数 ÷ その目的の要求の数 |
| 境界ごとの実装 | 要求の所属ファイル × カタログ | 要求が書かれたファイル名（拡張子なし）ごとの、実装登録済み ÷ 要求の数 |
| 受入基準の検証レベル | AC の `検証レベル` | レベルごとの AC の数（空は `-`） |
| System Test と ID 台帳 | 台帳 / ID 台帳 | ケースの `status` ごとの数。ID 台帳は 種別:状態 ごとの件数 |
| 実行履歴 | `docs/run-history.md` | 末尾 8 行を新しい順に。先頭 7 列まで |
| 設計・開発履歴と進捗 | 決定記録・実行履歴・要求・カタログ・台帳 | 分類（決定記録／実行履歴／要求状態／実装登録／System Test）× 状態の件数。押すと、根拠レコードのファイル:行を右に出します（VS Code で開くリンク付き） |

### 8.5.2 2D マップ・3D マップ（`#/map2d`・`#/map3d`）

同じ関係図（グラフ）を、平面と立体で表示します。点（ノード）の元になるデータは次のとおりです。

| 点の種類 | 元のデータ |
|---|---|
| 目的 | 要求定義書の目的 |
| 要求・受入基準 | 要求定義書（AC は「レイヤー」で追加表示） |
| パラメータ（PARAM）・質問 | 要求定義書の表（レイヤーで追加表示） |
| エンティティ | 状態の表、用語の表、要求の `対象エンティティ` |
| 共通部品・API・テーブル | カタログ |
| ファイル・コンポーネント | カタログの実装ファイル・テスト・各表の定義ファイル、台帳の `command` のパス。コンポーネントは、パスの先頭の 1〜2 階層（`src`・`app`・`apps`・`packages`・`services`・`lib`・`libs`・`modules`・`internal`・`cmd`・`pkg`・`projects` と `tests`・`test`・`__tests__`・`spec`・`specs` は 2 階層、そのほかは 1 階層） |
| 試験ケース | 台帳 |
| ペルソナ・外部連携 | 要求定義書の表（コンテキスト図で使う。2D/3D のレイヤーには出ません） |

| 線（関係） | 元のデータ |
|---|---|
| 目的 → 要求 | 要求の `上位` |
| 要求 → 受入基準 | 要求の AC |
| 要求 → エンティティ / PARAM / 質問 | `対象エンティティ`・`参照パラメータ`・BLOCKED の `Q-nnn` |
| 要求 → 要求（参照） | 要求本文・AC の本文に書かれた別の要求 ID |
| 要求 → 実装ファイル / テスト | カタログの機能の表の `実装ファイル`・`テスト` |
| 要求 → 共通部品 | 機能の表の `使っている共通部品`、共通部品の表の `使っている要求ID` |
| 要求 → API・テーブル | API・テーブルの表の関連する要求 |
| 共通部品・API・テーブル → ファイル | それぞれの `ファイル`・`定義ファイル` |
| 要求・AC → 試験ケース | 台帳の `requirement_ids`・`ac_ids` |
| 試験ケース → テストファイル | 台帳の `command` に含まれるパス |
| ファイル → コンポーネント | パスから決定 |

- 色の切替: 種別（点の種類）／決定状態（`statusKind`）／実装状況（done・none・unlisted）。
- 「強調」: 点にポイント＝直接の関連、クリック＝2 段先まで（`ref` 関係と、つながりが 36 を超える点は経由しません）。
- 点の位置（座標）は表示のために計算した値で、意味はありません。

### 8.5.3 図式（`#/diagrams`。`kind=` で種類を指定）

| 図（`kind`） | 読むデータ | 作り方 |
|---|---|---|
| コンテキスト図（`ctx`） | ペルソナ（4.1 の表）・外部連携（8 の表）・目的 | 中央にシステム、左にペルソナ（線のラベル＝`業務`）、右に外部連携（ラベル＝`方式`）。目的は中央の枠内に並べる |
| 目的ツリー（`goals`） | 目的・要求・カタログ | 目的ごとの要求を四角で並べる。色は実装登録か決定状態。青緑の枠は NFR。上位が不明な要求は「目的なし」の列 |
| 状態遷移図（`states`） | 状態の表（`対象エンティティ`・`状態`・`遷移…`） | エンティティごとの状態と遷移。二重枠は遷移先のない状態 |
| データ関連図（`entities`） | 要求の `対象エンティティ`、状態の表 | 同じ要求に出てきたエンティティを線で結ぶ。線の太さ＝共有する要求の数、丸＝状態の数 |
| コンポーネント図（`components`） | カタログのパス | コンポーネントと、その中のモジュール・共通部品・API・テーブル。線＝同じ要求を実装している |
| ER 図（`er`。タブには出ない補助表示） | 要求の `対象エンティティ`・`関係` | `関係` が書かれた要求だけ根拠付きで表示。書かれていないものは**推測せず**「関係情報が不足」と出す |

### 8.5.4 配置（`#/placement`）

| タブ（`tab`） | 読むデータ | 計算 |
|---|---|---|
| ビジネス層 × コンポーネント（`biz`） | 要求・目的・カタログ | 行は 目的／境界（要求の所属ファイル）／種別（FR・NFR-区分）から選ぶ。列はコンポーネント（実装ファイル数の多い順）。**セルの数 ＝ その行の要求のうち、そのコンポーネントに実装ファイルがある要求の数**。「テストを含める」でテストのコンポーネントも対象 |
| データ × コンポーネント（`data`） | 要求の `対象エンティティ`・カタログ | 行はエンティティ。セルの数は同様。下に API・テーブルの一覧 |
| 共通部品・API・テーブルの置き場（`items`） | カタログ | 部品・API・テーブルごとの、定義ファイルのあるコンポーネントと要求の数 |
| アプリ構成とデータ位置づけ（`kind=runtime`） | 読み込めたファイルの一覧・カタログの実装ファイル・外部連携 | 次の 8.5.5 |

### 8.5.5 配置（実行環境）（`#/placement?kind=runtime`）

Studio **自身**の動きを、読み込んだファイルから組み立てた図です。

| 表示 | 読むデータ |
|---|---|
| PC・ブラウザー・Studio サーバー・対象リポジトリ | 起動環境の値（リポジトリのパス、`/api/model`、`studio.py`）。固定の説明 |
| 管理データ: <パス> | 実際に存在した管理データのパス（8.1。`requirements_dir` と `manual_tests` も、存在すれば含む） |
| 実装ファイル: <パス> | カタログの機能の表に書かれた実装ファイルのパス（重複を除く） |
| 流れの表 | 管理データ→Studio サーバー（読取）、カタログ→実装ファイル（読取（登録位置）。名前だけ）、サーバー→ブラウザー（読取）、Studio→対象リポジトリ（書込: なし）。右の根拠欄にパス |
| 外部／クラウド境界 | 要求定義書の外部連携（方式・方向・正本） |

### 8.5.6 ソース対応（`#/source`）

| 表示 | 読むデータ | 計算 |
|---|---|---|
| ツリーマップ | カタログのパス（実装・テスト・部品・API・テーブルの定義ファイル）、台帳の `command` のパス | 面積 ＝ `1 ＋ そのファイルに結び付く要求の数`。大きな枠＝コンポーネント。青＝実装、緑＝テスト |
| ファイル一覧 | 同上 | コンポーネントごとに折りたたみ。結び付く要求の数と、部品・API・テーブルの名前。`↗` は `vscode://file/<リポジトリ>/<パス>` を開く（Studio は開かない） |
| 絞り込み | パスの文字列 | 全角・半角と大文字・小文字を区別せず、パスに含まれるか |

### 8.5.7 表（`#/tables?tab=`）

全タブとも、行を選ぶと図で強調され（`選択に関連する行だけ` で絞れ）、見出しで並べ替え、`CSV` でそのタブの**全行**（絞り込み前）を書き出せます。

| タブ（`tab`） | 読むデータ | 列 |
|---|---|---|
| 要求（`reqs`） | 要求定義書 ＋ カタログ（実装） | ID・題名・決定状態・優先度・目的・実装（done/none/unlisted）・AC の数・BLOCKED・境界（所属ファイル名） |
| 受入基準（`acs`） | 要求の AC | ID・要求・検証レベル・BLOCKED・本文 |
| 試験ケース（`cases`） | 台帳 `cases[]` | ID・題名・要求・AC・層（`layer`）・状態（`status`）・最終実行（`last_run_at`） |
| 共通部品（`parts`） | カタログの共通部品の表 | 名前・用途・ファイル・要求の数 |
| API・テーブル（`apis`） | カタログの API・テーブルの表 | 種別・名前・正本のシステム・定義ファイル・要求 |

### 8.5.8 構造（`#/structure`）

ナビゲーションには出ないページです（URL で開きます）。**7 つのデータ層**ごとに、現状（解析した件数）と理想（判定の基準）を比べ、1 レコードずつ判定した行を一覧にします。

| 層 | 読むデータ | 主な判定（差分の種別） |
|---|---|---|
| 要求定義書・境界別要求 | 要求・目的・AC | 不足（決定状態・AC がない）、孤立（`上位` の目的が存在しない）、参照不整合（AC 本文の ID が未定義）、重複（同じ要求 ID）、妥当 |
| カタログ | 機能の表 × 要求 | 余剰（要求にない行）、重複（同じ要求の行が複数）、参照不整合（決定状態が要求と違う）、妥当 |
| System Test | 台帳 × 要求・AC・PARAM | 重複（ケース ID）、参照不整合（未定義の要求・AC、AC の親要求が不一致、AC 本文の digest が台帳の `ac_digests` と不一致）、妥当 |
| ID 台帳 | ID 台帳 × 要求・AC・目的 | 余剰（定義のない ID）、参照不整合（接頭辞と種別が不一致）、重複、妥当 |
| 実行履歴 | `run-history.md` × 要求・ケース | 参照不整合（存在しない要求・ケースを参照）、重複（run-id）、妥当 |
| 境界間 | 外部連携の表 | 不足（方式・方向・正本が空）、重複、妥当 |

- 各行に `根拠`（ファイル:行）が付きます。
- AC の digest は、AC 本文の `{PARAM-nnn}` を値に置き換え、空白を詰めた文字列の SHA-256 先頭 16 桁です（`sha256:` 付き）。本文を変えたのに台帳を更新していないと「参照不整合」になります。
- 内容の確かさ（意味の矛盾など）は判定しません。それは `python scripts/verify.py` と rd-auditor の役割です。

### 8.5.9 一貫性（`#/consistency`）

ナビゲーションには出ないページです。要求 ID ごとに、5 つの層に記録があるかを調べます。

| 列 | ○（✓）の条件 |
|---|---|
| 要求 | 要求定義書にその ID の要求がある |
| AC | その要求に受入基準が 1 つ以上ある |
| 試験 | 台帳のケースの `requirement_ids` にその ID がある（`status` は見ません） |
| カタログ | カタログの機能の表にその ID の行がある |
| 実装ファイル | その行の `実装ファイル` にパスが 1 つ以上ある |

判定は、5 つともそろえば「正常」、1 つでも欠ければ「一層欠落」、カタログに行があるのに要求がなければ「参照先なし」です。

### 8.5.10 整合性保守（`#/maintenance`）

| 表示 | 読むデータ | 条件 |
|---|---|---|
| 保守候補 | カタログの機能の行 × 要求 | 行の `題名` か `決定状態` が、要求正本（見出しの題名・`決定状態`）と**文字列として異なる**行。要求正本に存在しない行は「未対応」として表示 |

実行（書き込み）の条件は 8.9 です。

## 8.7 欠けたときの見え方

| 欠けたもの | 見え方 |
|---|---|
| 要求定義書も要求ファイルもカタログもない | `--check` は終了コード 1。起動すると案内を出して終了。起動後に切り替えた場合も「データ層が見つかりません」で切り替わらない |
| カタログがない | 実装登録 % は 0。ソース対応・配置は空（「カタログにファイルの対応がありません」） |
| 台帳がない・JSON が壊れている | 試験合格 % は 0、試験ケースは 0 件。壊れているときは警告（`ledger is not valid JSON`）を記録 |
| ID 台帳・実行履歴がない | 該当の欄が空。構造の層は「判定対象 0 件」 |
| `実装ファイル` が `—`・未実装 | 要求の実装は none（未登録）。一貫性は「一層欠落」 |
| 列名が違う表 | 見分けられない表は読みません。`--check` の件数（0 件）と、`04-troubleshooting.md` の「画面に出ない」を見てください |

## 8.8 読まないもの

- ソースコード・設定・ログ・`work/` の中身（run の進捗・証跡・監査結果）。名前として出るのは、カタログと台帳に書かれたパスだけです。
- `docs/manual-tests.md` の中身（存在確認だけ）。
- `.github/`（エージェント・skill・hook）の中身。
- 要求定義書の利用シナリオ（解析はするが表示しない）。

## 8.9 書き込むもの

通常の閲覧・検索・CSV・リポジトリ切替では何も書きません。

書き込みは、整合性保守で `確認して実行` を押したときの **`docs/catalog.md` だけ**です。選んだ要求の行の `題名` と `決定状態` の 2 つのセルを、要求正本に合わせます。

1. プレビュー: 変更前後を表示し、トークンを発行します（ファイルは変えません）。
2. 実行: ファイルの内容が、Studio の起動時（または前回の適用後）から変わっていないことを確認します。変わっていれば `preview-conflict` で止まります（別の手段でカタログを更新したあとは、Studio を起動し直してください）。
3. 同じフォルダーに一時ファイル（`.eabk-studio-*`）を書いて置き換え、`python scripts/verify.py --docs-only` を実行します（`scripts/verify.py` がなければ読み取りの検査だけ）。
4. 失敗（検査の失敗・書込みの失敗・対象外ファイルが同じ実体を指す）したら、**元のバイト列と時刻・権限に戻して**エラーを表示します。

## 8.10 HTTP API（`127.0.0.1` だけ）

| メソッド・パス | 内容 |
|---|---|
| `GET /` ・ `GET /<パス>` | `EABK-Studio/web/` の静的ファイル（外のパスは 404） |
| `GET /api/model` | 解析した全データ（JSON）。更新時刻の指紋が同じなら、キャッシュを返す |
| `GET /api/fingerprint` | 管理データの更新の指紋（リポジトリのパス ＋ 各ファイルの更新時刻・サイズ） |
| `GET /api/repo` | 現在の対象リポジトリのパス |
| `POST /api/repo` | 対象リポジトリの切替（本文 `{"path": …}`）。`X-EABK-Studio: 1` が必要 |
| `POST /api/maintenance/preview` | 本文 `{"id": "<要求ID>"}`。同じヘッダーが必要 |
| `POST /api/maintenance/apply` | 本文 `{"token": …}`。同じヘッダーが必要 |

- 待ち受けは `127.0.0.1`（既定のポートは 8765。使用中なら次の番号を最大 20 まで試す）。`Host` ヘッダーが `127.0.0.1`・`localhost`・`::1` 以外の要求は 403 で拒否します。
- POST は、ヘッダー `X-EABK-Studio: 1` がなければ 403 です（ほかのサイトからの送信を避けるため）。本文は 8 KB まで。
- 外部のサーバーへは何も送りません（フォント・CDN・解析も使いません。3D 用の three.js は同梱）。
