## 1. 概要

### 1.1 事業背景

EABK は、要求定義から検証・実装・統合・報告までを run として継続実行する開発キットである。run の worktree と一時作業資産は処理を分離する一方、完了後に残り続けると利用者のディスクと作業一覧を圧迫する。早すぎる削除は診断・再開・未統合成果を失わせるため、統合済みの正常完了 run だけを、所有権を確認して清掃する。

### 1.2 目的

| ID | 目的 | 成功指標 | 測定方法 |
|---|---|---|---|
| G-004 | main 統合後検証まで成功した正常完了 run の一時資産だけを除去し、失敗した run の再開可能性と利用者・他 run の資産を保護する | 対象となる正常完了 run では AC-057〜AC-068 が pass し、対象外資産の削除が 0 件 | System Test の証跡、対象テスト、verify の終了コード、Git worktree 一覧、ファイルシステム、run-report を照合する |
| G-005 | EABK のデータ層（要求定義書・カタログ・台帳など）の不整合を、人の介在なしに早期に検出・修復し、直らないものだけを人に引き継ぐ | main と PR のデータ層検査の失敗のうち、機械的に直せるものは人手を要さずに解消され、直せないものは 100% が未解決 Issue として追跡される | AC-105〜AC-114 の自動テスト結果と、ワークフロー実行履歴・Issue 一覧を照合する |

### 1.3 事業妥当性の判定

根拠あり。完了済み run の資源回収と、失敗時の診断・再開資産の保持を同時に満たす。ただし実装時には、現在の main 統合前清掃を廃止または順序変更し、配布物とガイドを同時に更新することが条件である。

## 2. 対象と対象外

- 対象: EABK run が作成し、run の記録から所有権を確定できる pool worktree、作業ブランチ、統合ブランチ、run 固有の一時作業資産、および清掃の判定・報告。
- 対象: ローカル main へ自動統合できる run と、Windows を含む EABK 対応環境。
- 対象外: main への push、外部システム、利用者が作成した worktree・ブランチ、他 run の資産、所有権を確定できない資産。
- `run-report.md` は清掃の診断記録として保持し、本要求の即時削除対象にしない。正常完了 run の report は既存の保持期間による別の清掃に従うが、失敗 run の report と再開に必要な run 所有資産は、利用者が再開を放棄して削除を明示確認するまで、保持期間ベースの自動清掃の対象外とする。

## 3. 前提・制約

### 3.1 既定制約

- 本製品は Python スクリプト、Git 操作、Markdown の報告で動く CLI/バッチ型ツールであり、利用者が操作する画面を持たない（SRC-015、SRC-016）。このため、要求定義プロンプトの ui_policy-1（変更可能な画面レイアウト）と ui_policy-2（画面上のペルソナ別情報表現）は適用しない。
- main への push、外部システムの変更、デプロイは本依頼の対象外である（SRC-014）。
- 削除可否を証明できない資産は削除しない。清掃の網羅性よりデータ保護を優先する。

### 3.2 パラメータ（PARAM）

G-004 の要求では、利用者判断が必要な閾値・期間・件数を新設していない。G-005 の PARAM は次のとおり。

| ID | 名前 | 値 | 単位 | 根拠 | 決定状態 |
|---|---|---|---|---|---|
| PARAM-013 | データ層検査の定期実行間隔 | 1 | 週（1 日 1 回〜1 週 1 回の範囲で変更可） | 手動変更なしでも drift（ずれ）を検出できる最小頻度。変更しても他要求に影響しない | 承認済み（包括承認 2026-10-14・安全範囲は推奨どおり） |

## 5. 利用シナリオ

1. run は実装・検証・報告を終え、結果を確定する。
2. 結果が全件完了の場合だけ統合ブランチを main に統合し、main 上で検証する。
3. 統合と検証が成功した場合だけ、当該 run の所有資産を列挙し、保護対象を除外して清掃する。
4. 途中失敗、blocked、中止、競合、検証失敗、所有権不明、未コミット変更がある場合は資産を保持し、理由を報告する。
5. 清掃が中断した場合は、残された診断情報から安全に再試行する。

## 6. 要求

### 6.1 機能要求

#### FR-1009 正常完了 run の統合後清掃
- 要求: EABK は、run の結果が全件完了で、その成果を main に統合して統合後検証に成功し、正常完了 run になった場合だけ、その run が作成した清掃候補を除去できる。
- 決定状態: 承認済み（依頼 2026-10-10）　出自: 依頼原文　優先度: MUST（統合前の成果喪失を防ぎながら完了後の資源を回収するため）
- 上位: G-004　出典: SRC-014
- 対象エンティティ: EABK run、run 所有資産　関係する状態: 統合待ち→統合済み→清掃許可→清掃済み、清掃候補→削除済み　参照パラメータ: なし

- 受入基準 AC-059: 清掃が成功したとき、清掃候補となった当該 run の pool worktree、作業ブランチ、統合済みの統合ブランチ、一時作業資産は Git の登録とファイルシステムから除去され、main の統合結果は残る。
  - 検証レベル: integration

- 決定状態: 承認済み（依頼 2026-10-10）　出自: 依頼原文　優先度: MUST（誤削除の調査と途中失敗からの再開に必要なため）
- 上位: G-004　出典: SRC-014、SRC-015、SRC-016
- 対象エンティティ: EABK run、run 所有資産　関係する状態: 統合済み→清掃許可→清掃済み、清掃許可→保持、保持→清掃許可→清掃済み、統合済み→保持→再開不能、使用中→清掃候補→削除済み、清掃候補→保護　参照パラメータ: なし
- 関連する既存資産: 共通部品「run 状態・完了記録」、共通部品「run 作業資産清掃」、共通部品「conductor 終了契約」、共通部品「run 運用ガイド」
- 受入基準 AC-060: main 上の統合後 verify の成功後、清掃を開始する前に、正常完了、main の統合 commit、完了条件・最終 verify・対象テスト・main 上の統合後 verify の構造化結果、清掃候補、保護または保持する資産と理由を含む清掃前版 run-report が確定する。清掃中はその版の候補別結果欄だけに追記でき、清掃後に各候補の削除・保持・失敗結果と run の最終状態を含む清掃後最終版 run-report が確定し、その後に正常終了の完了記録を行う。
  - 検証レベル: system
- 受入基準 AC-061: いずれかの清掃操作が失敗した場合、EABK は失敗を成功として扱わず、以後の安全性を確認できない削除を停止し、候補別の成功・失敗・未実行結果を run-report に追記して保持状態を確定し、main の統合結果、run-report、診断情報、未削除資産を保持して非 0 で終了する。
  - 検証レベル: integration
- 受入基準 AC-062: 清掃操作失敗で保持中の run を再実行した場合、清掃前版 run-report と候補別結果を照合し、既に削除済みの当該 run 所有資産を成功済みとして扱い、残存する清掃候補だけを再評価する。残存候補の所有権と安全性の再判定に成功したときだけ保持から清掃許可へ戻り、他の資産を対象に広げずに清掃後最終版 run-report を確定できる。
  - 検証レベル: integration

## 1. 概要

### 1.1 事業背景

EABK の要求定義書、カタログ、System Test 台帳、ID 台帳、実行履歴は、複数の人と AI エージェントが引き継いで開発するための管理データである。EABK Studio はその管理データを開かずに横断して読み、要求・実装・試験・履歴の対応と不足を把握できるローカル専用 Web アプリである。現状は管理データを個別に読む摩擦があり、目的に対する進捗、実装登録率、未回答、BLOCKED、出典、ソース対応の判断を一つの視点で行いにくい。

### 1.2 目的

| ID | 目的 | 成功指標 | 測定方法 |
|---|---|---|---|
| G-001 | 管理データの関係を読み取り、目的から要求・実装・試験までを一貫して確認できるようにする | ダッシュボード、地図、図式、表、ソース対応で同一 ID の関係を辿れる。System Test の達成判定では、台帳の分母を登録済み system AC とし、`pass` のみを合格、`fail` と `blocked` と `not_run` を未達または未判定として扱い、判定時点を併記する | 承認済み範囲は AC-001〜AC-006、AC-023〜AC-024、AC-037、AC-045、AC-048〜AC-053 を System Test で確認する。承認待ちの AC-021〜AC-022 は承認後に限り条件付き指標へ加える |
| G-002 | Product Manager、Architect、Software Engineer が各自の判断に必要な表現を初期状態から得る | 3 ペルソナの既定表現と代替表現が要求・AC・出典で確認できる | 承認済み範囲は AC-007〜AC-012、AC-026〜AC-027、AC-044、AC-048〜AC-052 を確認する。承認待ちの AC-025 は承認後に限り条件付き指標へ加える |
| G-003 | 管理データの鮮度、整合性、未解決事項を安全な読取で可視化する | 自動再読込、フィンガープリント、未回答、BLOCKED、状態表示が確認できる。登録・実装・証跡・実行・合格を別状態として表示し、承認待ち要求を実装済みまたはリリース済みの達成数に含めない | 承認済み範囲は AC-013〜AC-020、AC-028〜AC-035、AC-045〜AC-051 を確認する |

目的の達成判定は、上記の目的別「承認済み範囲」に列挙した AC がすべて `pass` の場合だけ達成とする。1件でも `fail` または `blocked` があれば未達、`not_run` があれば未判定とし、複数状態がある場合は未達を優先する。条件付き指標は対応する要求の承認後に別集計し、承認前の目的達成判定には混在させない。

### 1.3 受益者・費用負担者・決定権者

受益者は上記 3 ペルソナと要求定義・実装・試験の担当者である。費用負担者と要求の最終決定権者は依頼に明示されておらず、Q-001 で確認する。事業妥当性は **条件付き** とする。既存のローカル専用・追加インストール不要・管理データ読取という実装事実（SRC-001〜SRC-003）により小さく始められるが、権限、保存単位、外部連携、証跡、アクセシビリティの判断が未回答であるため、共有運用への拡張は保留する。

## 2. 対象と対象外

**対象**: `docs/requirements-definition.md`、`docs/requirements/*.md`、`docs/catalog.md`、`tests/system/ledger.json`、`docs/id-registry.md`、`docs/run-history.md` および `scripts/ebak.config.json` で指定された管理データの読取・解析・可視化、リポジトリ切替、検索、図式、配置、表、ソース対応、JA/EN 表示、更新検知、ならびに FR-1004 の利用者が明示的に開始する整合性保守。

**対象外**: FR-1004 以外の管理データへの書込み・自動修正、README・コード・テスト・設定の生成や変更、外部サービスへの接続、認証・認可の正本化、共同編集、利用者データの永続保存、外部公開、削除・移行など不可逆操作。これらを必要とする要求は Q-001〜Q-004 の回答まで BLOCKED とする。ただし FR-006 の CSV 出力は、利用者の明示操作で表示対象の管理データから一時生成し、ブラウザーのダウンロード先へ引き渡す非永続の出力であり、管理データまたはサーバー側への書込みには含めない。

## 5. 利用シナリオ

1. 利用者は対象リポジトリを既定値で起動し、管理データを読込む。
2. Product Manager はダッシュボードから目的・進捗・未回答・BLOCKED を選択し、2D マップまたは表へ移る。
3. Architect は 2D/3D マップ、配置、図式で関係と層を確認する。
4. Software Engineer は検索、表、ソース対応、状態遷移で要求から試験までを確認する。
5. 読込中に管理データが更新された場合、利用者へ鮮度を示し再読込する。
6. リポジトリ切替が入力不備または管理データ不足で失敗した場合、現在の表示を失わず原因と次の行動を示す。
7. 支援への引継ぎは、ID、出典、状態、カタログのパスをテキストまたは CSV で共有する。認証付き共有や監査証跡は Q-001、Q-004 の回答待ち。

#### FR-1016 許容時間を指定するだけの実装依頼（/build 入口）の生成
- 要求: EABK の利用者は、許容時間（例: 60分、24時間）だけを指定して、FR-1015 の分析にもとづく `/build` 用の依頼（`<request>`・`<answers>`・`<references>`・`<run_options>`）を生成できる。生成された依頼の `max_hours` は指定した許容時間に等しく、`scope` は許容時間に収まる件数の次実装候補の要求 ID である。生成だけを行い、run の開始・実装・commit は行わない。
