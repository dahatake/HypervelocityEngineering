1. 概要

1.1 事業背景

EABK は、要求定義から検証・実装・統合・報告までを run として継続実行する開発キットである。run の worktree と一時作業資産は処理を分離する一方、完了後に残り続けると利用者のディスクと作業一覧を圧迫する。早すぎる削除は診断・再開・未統合成果を失わせるため、統合済みの正常完了 run だけを、所有権を確認して清掃する。

1.2 目的

ID 目的 成功指標 測定方法
G-004 main 統合後検証まで成功した正常完了 run の一時資産だけを除去し、失敗した run の再開可能性と利用者・他 run の資産を保護する 対象となる正常完了 run では AC-057〜AC-068 が pass し、対象外資産の削除が 0 件 System Test の証跡、対象テスト、verify の終了コード、Git worktree 一覧、ファイルシステム、run-report を照合する
G-005 EABK のデータ層（要求定義書・カタログ・台帳など）の不整合を、人の介在なしに早期に検出・修復し、直らないものだけを人に引き継ぐ main と PR のデータ層検査の失敗のうち、機械的に直せるものは人手を要さずに解消され、直せないものは 100% が未解決 Issue として追跡される AC-105〜AC-114 の自動テスト結果と、ワークフロー実行履歴・Issue 一覧を照合する

1.3 事業妥当性の判定

根拠あり。完了済み run の資源回収と、失敗時の診断・再開資産の保持を同時に満たす。ただし実装時には、現在の main 統合前清掃を廃止または順序変更し、配布物とガイドを同時に更新することが条件である。

2. 対象と対象外

  • 対象: EABK run が作成し、run の記録から所有権を確定できる pool worktree、作業ブランチ、統合ブランチ、run 固有の一時作業資産、および清掃の判定・報告。
  • 対象: ローカル main へ自動統合できる run と、Windows を含む EABK 対応環境。
  • 対象外: main への push、外部システム、利用者が作成した worktree・ブランチ、他 run の資産、所有権を確定できない資産。
  • run-report.md は清掃の診断記録として保持し、本要求の即時削除対象にしない。正常完了 run の report は既存の保持期間による別の清掃に従うが、失敗 run の report と再開に必要な run 所有資産は、利用者が再開を放棄して削除を明示確認するまで、保持期間ベースの自動清掃の対象外とする。

3. 前提・制約

3.1 既定制約

  • 本製品は Python スクリプト、Git 操作、Markdown の報告で動く CLI/バッチ型ツールであり、利用者が操作する画面を持たない（SRC-015、SRC-016）。このため、要求定義プロンプトの ui_policy-1（変更可能な画面レイアウト）と ui_policy-2（画面上のペルソナ別情報表現）は適用しない。
  • main への push、外部システムの変更、デプロイは本依頼の対象外である（SRC-014）。
  • 削除可否を証明できない資産は削除しない。清掃の網羅性よりデータ保護を優先する。

3.2 パラメータ（PARAM）

5. 利用シナリオ

  1. run は実装・検証・報告を終え、結果を確定する。
  2. 結果が全件完了の場合だけ統合ブランチを main に統合し、main 上で検証する。
  3. 統合と検証が成功した場合だけ、当該 run の所有資産を列挙し、保護対象を除外して清掃する。
  4. 途中失敗、blocked、中止、競合、検証失敗、所有権不明、未コミット変更がある場合は資産を保持し、理由を報告する。
  5. 清掃が中断した場合は、残された診断情報から安全に再試行する。

1. 概要

1.1 事業背景

EABK の要求定義書、カタログ、System Test 台帳、ID 台帳、実行履歴は、複数の人と AI エージェントが引き継いで開発するための管理データである。EABK Studio はその管理データを開かずに横断して読み、要求・実装・試験・履歴の対応と不足を把握できるローカル専用 Web アプリである。現状は管理データを個別に読む摩擦があり、目的に対する進捗、実装登録率、未回答、BLOCKED、出典、ソース対応の判断を一つの視点で行いにくい。

  1. 利用者は対象リポジトリを既定値で起動し、管理データを読込む。
  2. Product Manager はダッシュボードから目的・進捗・未回答・BLOCKED を選択し、2D マップまたは表へ移る。
  3. Architect は 2D/3D マップ、配置、図式で関係と層を確認する。
  4. Software Engineer は検索、表、ソース対応、状態遷移で要求から試験までを確認する。
  5. 読込中に管理データが更新された場合、利用者へ鮮度を示し再読込する。
  6. リポジトリ切替が入力不備または管理データ不足で失敗した場合、現在の表示を失わず原因と次の行動を示す。
  7. 支援への引継ぎは、ID、出典、状態、カタログのパスをテキストまたは CSV で共有する。認証付き共有や監査証跡は Q-001、Q-004 の回答待ち。

14. Vibe Coding Benchmark 共通品質要求

NFR-COR-001 再現性

  • 要求: ベンチマーク提出物は、同一 OS、同一ランタイム、同一入力で実行されたとき、同一の結果と終了コードを返し、日時または乱数を使う場合は固定値またはシードを指定できる。
  • 決定状態: 承認済み（依頼 2026-10-10）　出自: 依頼原文　優先度: MUST（実装手段によらず比較結果を再現できる必要があるため）

  • 検証レベル: integration

  • 要求: ベンチマーク提出物は、不正入力、未対応構文、参照エラー、I/O エラーを区別できるエラーコードを返し、例外を成功として扱わない。
  • 決定状態: 承認済み（依頼 2026-10-10）　出自: 依頼原文　優先度: MUST（異常系の成否を実装ごとに同じ方法で判定するため）
