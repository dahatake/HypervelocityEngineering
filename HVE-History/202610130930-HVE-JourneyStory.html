1.1 ストーリーの一文

Coding Agent がまだ弱かった時期に、私たちは人手の手順・レビュー・分割・オーケストレータで弱さを補った。モデルが強くなったとき、その補助輪が一番の足かせになった。そこで足場を外して測り直したら、残すべきものは「モデルの能力に依存しないもの（正本、決定的な検査、永続データ）」だけだった。その薄い足場の上で、コードから事業構想（Business Envisioning）まで同じやり方を広げている。

1.3 4 つの仮説の判定（詳細は §5）

# あなたの仮説 判定
H1 早期に取り組んだ人ほど、低性能なモデル向けの Best Practice が今の足かせになっている 支持（強い）。ただし言い直しが必要 — 足かせになったのは「能力不足を前提にした足場」。「能力に依存しない足場」は残る

H3 Vibe Coding で何のデータを保持すべきかは調査中 現状の理解として妥当。有力な候補は特定できたが、未解決の問いが残る
H4 Work IQ などの Knowledge 連携を Coding Agent が適切に行えるようになった 部分的に支持 — 「モデルに任せる設計」は正しいと確認できたが、認証と実行環境の条件が残る

3. ストーリー（章立て）

各章は「何をしたか → 何が起きたか → 失敗 → 発見 → 次への転換 → スライド化メモ」の順です。

第 0 章 出発点: 事業構想から始まった（01-23〜02）

何をしたか（事実） - リポジトリー名が示すとおり、題材は会員・ポイント・特典などを扱う業務システム（Royalty Service の 2 世代目）です。 - 最初の仕事は、コードではなく Future Scenario（未来シナリオ）の一覧 15〜20 件と、その詳細（FS01〜FS20） でした。cloud agent に Issue / PR で書かせ、PM 系の Custom Agent の指示書を整備しました。 - 02 月には UC-10 のユースケース → ドメイン分析 → マイクロサービス抽出へ進みました。

何が起きたか（事実） - 1 つの成果物を「3 つのサブタスクに分割」し、各サブタスクを書いたあとに「Review Cycle 4 / 5 / 6」「3 回レビューで 105 件の問題を修正」と、人が決めた回数だけ自己レビューを回しました。commit の履歴にそのまま残っています。 - cloud agent の PR マージは 1 月 13 件、2 月 108 件、3 月 376 件と増えました。

発見（推論） - この時期の分割とレビューの反復は、当時のモデルの出力上限・精度・長文の一貫性を補うための手順でした。その時点では合理的でした。 - そして、最初の題材が「事業構想」だったことは、のちの Business Envisioning への回帰として物語の伏線になります（第 9 章）。

スライド化メモ - キーメッセージ: 「最初の依頼はコードではなく、事業の未来シナリオだった」 - ビジュアル: 1 月の commit ログの抜粋（"Create Future Scenario list with 20 prioritized scenarios"）と、2 月の "Review Cycle 4/5/6" の並び - 実感を足す: 【実感を足す】 なぜ事業構想から始めたか

第 1 章 補助輪の時代: Best Practice で弱さを補う（02〜03 月）

何をしたか（事実） - Custom Agent を 02-20 時点で 19 本。02-24 に複数の Workflow を単一の orchestrator に置換しました。 - 03-02 に「A-exec 分割」を強制する、DAG 風の実行フローを Agent の指示書に入れる、受入基準の検証セクションを入れるなどを実施しました。 - ファイル数は 02-20 時点 69 → 03-31 時点 754 と、約 1 か月で 11 倍になりました。

何が起きたか（事実・推論） - 追加した手順は、どれも当時の弱さに対するもっともな処方でした。

当時の弱さ（推論） 当時の処方 今どうなっているか
1 回の出力が途中で切れる、長文の一貫性が崩れる 成果物を 3 つのサブタスクに分割。「1 回の書き込みは 300 行以内」 今も有効。 分割の 1 文（C1S）は Sonnet 5.5 でも成功率を 1/3 失敗 → 3/3 成功に変えた（EOS §3.3）
1 回で品質が出ない Review Cycle を固定回数。3 回レビュー 敵対的レビューの量産へ（§第 4 章）。reviewer を外すと AI クレジットは約 26% 減り、結果は変わらなかった（3 方式比較 §5.6）
途中で止まる、再開できない Workflow の連続実行、Step 単位の resume、実行台帳 Autopilot と再開で足りる（EOS §5.1 課題 1）
大きな作業を分けて並列に流せない DAG、Wave、ATG /fleet、サブエージェントで足りる。ATG は品質が同じで時間 1.7〜2.25 倍・費用 2.49〜3.50 倍（EOS §3.1）

発見（推論） - ここで大事なのは、「手順を足す」ことが、当時は正しい判断だったことです。この章を「失敗」とは呼びません。失敗は、足した補助輪を外すタイミングを測る仕組みがなかったことにあります（第 4 章）。

スライド化メモ - キーメッセージ: 「補助輪は、当時は正しかった」 - ビジュアル: 上の表（左: 当時の弱さ → 右: 今）。色分けで「今も有効 / 不要 / 逆効果」 - 実感を足す: 【実感を足す】 当時、何に困って最初の手順を足したか

第 2 章 手順がフレームワークになる: HVE v1 の誕生と成長（03〜06 月）

何をしたか（事実） - 03-18 に GitHub Copilot SDK のローカルオーケストレーター。03-31 に AQRC（QA 要求分類）Workflow。04-01 に Self-Improve ループ。04-21 に Work IQ の読み取り連携（QA / AKM / AQOD）。GUI、Fleet モード、Cloud Session を追加。 - 最終的な規模は、Workflow 13、Prompt 約 314 件、Skill 34 件、knowledge/ に D01〜D21、hve/ の Python 934 ファイル・約 27.7 万行です。 - 版は 06-09 の 0.1.1 から始まり、08-16 の 0.8.1 を経て、10-03 の 0.8.197 に至りました。8 月 24 日〜9 月 21 日の 4 週間だけで、0.8.40 から 0.8.132 まで約 90 回の版上げです。

何が起きたか（事実） - HVE は「業務要件の整理から設計・実装・検証までを、再現可能なワークフローとして運用する」ことを目的にしていました。 - 解こうとした課題は 10 個あり、あとの整理で次の 3 つに分類できました（EOS §5.1）。 - 7 個: Copilot 本体の機能か運用の規則で足りる（不要） - 3 個: リポジトリーごとの小さな仕組みで足りる（薄い仕組み）。偽の PASS、要件索引、費用と証跡 - 課題そのものは今も実在する。不要になったのは、解決のために Framework やアプリケーションを作り保守すること

失敗（事実） - HVE の開発・保守に 181,055 AIU（約 1,811 USD）。その仕組みで作った業務アプリは未完成でした（第 5 章）。

スライド化メモ - キーメッセージ: 「課題は本物だった。ただし、解き方（自作フレームワーク）は不要になった」 - ビジュアル: 10 個の課題 × 3 分類のマトリクス（EOS §5.1 の表を簡略化） - 数字: 0.8.1 → 0.8.197 を 48 日、約 27.7 万行

第 3 章 Knowledge をつなぐ: Work IQ の最初の設計と、その誤算（04 月〜10-01）

これは仮説 H4 の中心です。

何をしたか（事実） - 04-21 に Work IQ を、QA（事前の質問票）と知識化（AKM / AQOD）に読み取り専用で統合しました。 - 設計は「HVE が質問を最大 10 問に絞り、1 問につき 1 回だけ Work IQ に固定の形式で問い合わせる」。許可ツールは ask の 1 つ。応答は 1〜5 行の固定スキーマに押し込める、というものでした。
