# 開発フレームワークはもう不要なのか？ 2 つのアプリの開発履歴を比べて、Coding Agent に残したい規律を考えた

## 背景

AI にアプリケーションの実装を任せるとき、私は以前から少し気になっていたことがあります。

作業を最後まで進めるために、どこまで仕組みを用意するべきなのでしょうか。

要求を整理し、作業を分け、複数の Agent に役割を与え、結果を検査する。
それぞれには理由があります。

ただ、仕組みを動かすための作業が増え、肝心のアプリケーションを作る時間が長くなっているのではないか、とも感じていました。

私が検討してきた HVE と EABK も、この問題に向き合うための仕組みです。
当初は、長時間の作業を続けるために、独自のオーケストレーションや検査を積み上げることが有効だと考えていました。

その後、似た目的を持つ動画編集アプリを、EABK を使う場合と使わない場合の両方で開発しました。
一方は未完成のままで、もう一方は最初のリリース版に到達しています。

そこで、開発履歴、会話の記録、テスト結果と、別に行った小さな変更の比較実験を整理しました。

この記事で考えたい問いは、次の 1 つです。

**現在の Coding Agent を使うアプリケーション開発では、独自の開発フレームワークをどこまで残すべきなのでしょうか。**

先に私の立場を書くと、今回の条件では、以前のような重いオーケストレーションを最初から入れる必要性は下がったと考えています。
ただし、要求を明確にし、外部のテストで確かめることまで不要になったとは考えていません。

## 注意点 / 前提

:::note warn
**これは私自身の環境での 2 アプリの開発記録と、別の少数の比較実験です。** 対象のアプリ、時期、モデル、依頼、開発環境はそろっていません。観測した差を、フレームワークの有無だけが生んだとは言えません。
:::

- 記録を整理した日: **2026 年 11 月 8 日**。日時は日本時間です。
- 比較するアプリ: EABK 0.5.x を途中から使った動画編集アプリと、独自の開発フレームワークを使わなかった動画編集アプリです。
- 実行環境: 前者は主に VS Code Chat、後者は Copilot CLI の Autopilot です。前者には、別の PC の実行履歴も含まれます。
- 比較する EABK の版: 実際の導入例は **0.5.x** です。後からオーケストレーションを削減した **EABK Lite 0.6.0** の効果を、同じ条件で測ったものではありません。
- 完成の扱い: 「未完成」と「最初のリリース版」は私の評価です。後者も、第三者による盲検の受入評価は保留されています。
- 立場: 私は両方の開発を検討した当事者です。この記事は個人の記録と考察であり、特定の組織の公式見解や製品の一般的な性能評価ではありません。

個別のリポジトリー名、作業用のファイル名、フォルダー名、パス、コミットハッシュは掲載しません。
記録の引用でも、それらに当たる部分は `【ファイルパス省略】` などに置き換えます。

なお、この記事で「Coding Agent」と書くときは、コードを調査・変更・検証する Agent の総称として使います。
**Copilot CLI と、クラウドで動く GitHub Copilot coding agent は同じ実行環境ではありません。**
一方にある機能や、今回の結果を、そのまま他方に当てはめないようにします。

## HVE と EABK とは

比較の前に、読者にはなじみがないかもしれない仕組みを整理します。

### 何を解決しようとしたのか

AI に長い開発を任せると、作業の途中で止まる、前提を見失う、テストや要求との対応が分からなくなる、といった問題が起きます。

HVE と EABK は、私がそのような問題に対処するために使ってきた開発の仕組みです。
役割分担、要求の管理、検査を組み合わせ、実装の進行と成果物の整合性を扱います。

| 対象 | 構成と動き | 合否・制約の扱い |
|---|---|---|
| HVE v1 | Workflow、作業の依存関係を扱うオーケストレータ、Prompt、Skills などを組み合わせる | 長い作業の分割、継続、確認を独自の仕組みで支える |
| EABK 0.5.x | 進行役が作業役を使い、要求定義、実装、テスト、監査を進める | Hooks による操作の制限、要求とテストの台帳、決定的な検査を使う |
| EABK Lite 0.6.0 | 旧版の進行役・作業役によるオーケストレーションを削減し、規則、管理データ、検査、必要な節目の監査を残す | 通常の Agent への依頼を前提とし、ローカルや CI の検査で管理データを確認する |

ここでいう **決定的な検査** は、LLM の自己申告ではなく、決められた入力と規則に対してプログラムが合否を返す検査です。
ただし、要求 ID が存在することと、そのテストが本当に要求の意味を満たしていることは別です。

旧版の Hooks は実際に操作を拒否できます。
一方、Lite の文章による規則は、それだけで Agent の行動を強制するものではありません。
CI も、導入・設定され、実行結果が確認されて初めて検査として働きます。

### 入手・導入は別に確認する

EABK は、対象のアプリケーションに規則・要求管理のデータ・検査を導入して使う方式です。
利用する場合は、配布物の版、導入によって変わる内容、アプリ固有のビルド・テスト設定を確認する必要があります。

今回の資料には、個別のリポジトリー名を伏せたまま示せる EABK の公開一次資料の URL と、具体的な導入手順が含まれていません。
**【要確認：匿名化したまま案内できる公開配布先、一次資料の URL、対象版に対応した導入手順】**

以下で扱う旧版の負担を、そのまま Lite の測定結果と混同しないでください。

## 整理・考え方

### 比較対象と出発点を分けておく

以降は、同じ順序と呼び方で比較します。

| 条件 | 導入例（EABK 0.5.x） | 非導入例（独自フレームワークなし） |
|---|---|---|
| 開発の形 | Windows デスクトップアプリ。途中から EABK を導入 | ローカルの Web アプリ。Copilot CLI の Autopilot を使用 |
| 目的 | 長い動画から、長尺版や短尺版などを編集する | 長い動画から、SNS 向けの短尺版や長尺版などを編集する |
| 共通する機能 | 動画の取り込み、文字起こし、見どころの抽出、字幕など | 同左。ただし、機能の詳細と範囲は同一ではない |
| 要求の記録 | 98 件。EABK 導入前から開発 | 103 件。調査から PRD を作成して実装 |
| 主なモデル | 導入前と導入後で異なる。導入後の記録には Claude Sonnet 5.5 と Claude Opus 5.5 を含む | 主に Claude Opus 5.5。ほかのモデルの呼び出しもある |
| 合否の材料 | 要求・受入基準、管理データ、テスト、実行履歴 | PRD、実装、テスト。第三者の盲検受入は保留 |
| 2026 年 11 月 8 日の評価 | 未完成 | 最初のリリース版 |

要求の件数は近いのですが、粒度も実装する機能も同じではありません。
コードの量も、導入例が約 29.8 万行、非導入例が約 1.4 万行です。
**要求の件数が近いことは、難しさや完成度が同じことを意味しません。**

### 比較軸を分けておく

この記事では、次の 4 つをこの順番で見ます。

1. **条件と成果**: 何を、どの環境から、どの状態まで作ったか。
2. **所要時間と手戻り**: 記録された時間と、再開・残作業の依頼がどれだけあったか。
3. **品質と要求の追跡**: テスト、要求との対応、外部の受入がどうなっていたか。
4. **費用と運用負荷**: Token や変更量、Agent の費用の代理指標が何を示すか。

### 「時間」「費用」「品質」は別に考える

今回のジョブ時間は、人の Prompt から、次の人の Prompt より前にある最後の Agent のイベントまでの区間です。
承認待ちや PC の停止など、人が実際に操作していない時間を含み得ます。
並行した区間があれば、合計は壁時計上の経過時間とも一致しません。

導入例の後半には、このジョブ時間ではなく、実行履歴に記録された run の経過時間もあります。
したがって、両者の単純合算は **人の労働時間でも、厳密に同じ測定単位の実行時間でもありません**。

Token はキャッシュからの読込を含む入力 Token です。
また、記録されたモデルの `cost` は課金倍率の合計として扱っており、実際の請求額ではありません。
テスト件数も、アプリの品質や実利用での安全性を単独で示すものではありません。

## 検証

### 1. 条件と成果: 2 つのアプリはどこまで進んだか

**目的** は、似た目的の開発が、それぞれどのような条件で始まり、どの状態に至ったかを確かめることです。

**入力と手順** は、開発履歴、Agent の会話イベント、EABK の実行履歴、要求とテストの記録を確認し、報告書の条件で集計することでした。
非導入例は 11 セッションの人の Prompt を集計しています。
導入例には、会話の記録が欠けている期間と、Token が記録されていない期間があります。

| 観点 | 導入例（EABK 0.5.x） | 非導入例（独自フレームワークなし） |
|---|---|---|
| 対象期間 | 2026 年 8 月 26 日から 11 月 7 日まで。未完成 | 2026 年 11 月 7 日から 11 月 8 日まで。最初のリリース版 |
| 開発の出発点 | 導入前から進めていたアプリに EABK を適用 | 調査・PRD を作成し、アプリを実装 |
| 利用した記録 | 導入前と導入後の会話、後半の run の履歴。一部期間は会話記録なし | 11 セッション、28 件の人の Prompt |
| 記録上の要求 | 98 件 | 103 件 |
| コードの規模 | 約 29.8 万行 | 約 1.4 万行 |
| 外部の受入 | 未完成 | 盲検の受入評価は保留 |

非導入例では、調査、PRD、主実装、その後の変更という流れが記録されています。
導入例も、最初は調査と計画から始まっています。
違いは、アプリ自体やモデルのほか、後に EABK を導入したこと、依頼の切り方、その時点までに得た経験などです。

**分かったこと** は、今回、非導入例が最初のリリース版に到達した一方、導入例は未完成だったことです。

**分からなかったこと** は、両者が同等の受入基準を満たすまでに必要な仕事の量と、その差のうち EABK が原因となった割合です。

### 2. 所要時間と手戻り: 長い作業はどこにあったか

**目的** は、フレームワークの有無だけでなく、同じ導入例の導入前と導入後も見ることでした。

**条件** として、導入例の会話が記録されていた期間を、導入前と EABK 導入後に分けました。
導入後のさらに後半は、会話イベントではなく run の経過時間です。

| 観点 | 導入例（EABK 0.5.x） | 非導入例（独自フレームワークなし） |
|---|---|---|
| 人の Prompt・介入 | 導入前 135 件、導入後の会話記録 44 件、後半 run への介入約 33 件。未記録期間あり | 28 件 |
| 記録された区間長 | 導入前 272.6 時間、導入後の会話 38.4 時間、後半 run 100.6 時間。単純合算 411.6 時間 | 14.3 時間 |
| 2 時間を超えるジョブ | 導入前 37 件、導入後の会話 7 件。後半は 30 run 中 19 件 | 0 件 |
| 長い作業の例 | 導入前の最長ジョブ 1,154.7 分。後半 run の最長 33.6 時間 | 最大ジョブ 99.5 分 |
| 再開などの依頼 | 導入前は再開・状況確認など 24 件。導入後の会話では 5 件 | 再開・状況確認の Prompt は 0 件。未実装の完了依頼は 1 件 |
| 後半 run の完了 | 30 run のうち 15 件が全件完了 | 対応する run の記録なし |

数字だけを見ると、導入例の単純合算は非導入例の約 29 倍です。
正直、この差は思っていた以上に大きいものでした。

ただし、これは「EABK によって 29 倍遅くなった」という数字ではありません。
導入例の **272.6 時間は EABK 導入前**です。
さらに、後半には異なる単位の run 時間が含まれ、記録のない期間もあります。

導入前の記録では、残作業をまとめて依頼した区分が 71 件、再開・状況確認などの区分が 24 件ありました。
この 2 区分の区間長は合計 231.1 時間で、導入前の 272.6 時間の約 85% です。
分類は Prompt の文面を使った機械的なもので、人の作業内容を直接測ったものではありません。

導入後の会話記録では、残作業をまとめて依頼した区分は 1 件でした。
**EABK の導入後に、依頼の形が変わったことも観測されています。**
ただし、時期やモデルも変わっているため、これも EABK 単独の効果とは決められません。
後半の未完了 run には画面ロックなどの環境要因も含まれており、すべてを EABK 自体の故障とは扱えません。

### 3. 品質と要求の追跡: テストが通れば十分なのか

**目的** は、速さだけでは見えない品質上の違いを確かめることでした。

**手順** として、テストの結果、要求と実装・テストの対応、要求定義の更新、外部受入の状態を調べました。

| 観点 | 導入例（EABK 0.5.x） | 非導入例（独自フレームワークなし） |
|---|---|---|
| 自動テストの記録 | テストメソッド 3,717 件。最後の run では対象の受入基準 30/30 が合格 | 調査時に 151 テストが合格 |
| 要求の対応記録 | 98 件中 55 件に実装ファイルとテストの記載。43 件は未確認 | 103 件中 56 件が、コード **または** テストに結び付いたとツールが判定 |
| 要求定義の更新 | 要求定義の変更や、監査で見つかった矛盾への修正を記録 | 主実装後の追加機能の一部が PRD に追従していない |
| 外部の受入 | 未完成 | 盲検の受入評価は保留 |

**43 件の「未確認」は「未実装」の意味ではありません。**
また、55/98 と 56/103 は判定方法が異なります。
前者はカタログの記載、後者はコード **または** テストへの結び付きをツールが検出した件数です。
54% と 56% という数字を、同じ方法で測った品質スコアとして比較することはできません。

非導入例では、シリーズ分割などの追加機能が PRD に十分書き戻されていませんでした。
後から追加されたテストにも、要求 ID を参照していないものがありました。
**151 テストの合格と、要求定義が最新であることは別です。**

一方、導入例では、要求の矛盾や旧版からの条件の退行を監査で見つけ、修正した記録があります。
EABK にかかった手間のすべてが無駄だった、とも言えません。
ただし、管理データの検査に合格することだけで、アプリ全体の動作や外部受入まで保証されるわけではありません。

### 4. 費用と運用負荷: 何に変更と呼び出しが使われたか

**目的** は、アプリの実装以外に必要だった作業と、モデル利用の記録を分けて見ることでした。

**条件** として、変更行数は追加行と削除行の合計です。
同じ行を何度も変更すれば、その都度数えられます。
費用は実請求額ではなく、記録上の課金倍率の合計です。

| 観点 | 導入例（EABK 0.5.x） | 非導入例（独自フレームワークなし） |
|---|---|---|
| 入力 Token | 記録のある導入前・導入後の会話で約 90.7 億。後半 run は記録なし | 約 4.1 億。キャッシュ読込を含む |
| 変更量 | EABK 導入期の追加・削除は 124,862 行 | 全期間の追加・削除は 24,836 行 |
| 変更の内訳 | 導入期のうち、ツールキット・フレームワークに分類された変更が 61,742 行、約 49%。アプリ本体は 27,632 行、約 22% | アプリ本体に分類された変更は 14,813 行、約 60% |
| モデル費用の記録 | 比較可能な全期間の記録はない | 課金倍率の合計 20,889。実際の請求額ではない |
| 運用上の失敗 | Hooks の誤拒否、画面ロックやデスクトップの取り合いなどで作業が止まった記録 | PRD と後続の変更がずれた記録 |

変更行数の約 49% は、EABK 導入期の変更を、報告書でツールキット・フレームワークに分類した割合です。
**開発者の時間や費用の 49% が EABK のために使われた、という意味ではありません。**
分類には導入や更新に伴う変更が含まれ、後から同じ行を変更した分も数えます。

また、EABK の経過時間や Token が大きくても、モデルの課金倍率が異なれば、実際の費用の順序は変わり得ます。
別の少数の依頼の比較では、非導入例の方が高価なモデルを使ったため、課金倍率の合計の中央値は高くなっていました。
Token、時間、モデル単価を 1 つの「コスト」にまとめない方がよさそうです。

### 5. 期待と違った結果: フレームワークがない開発にも失敗はあった

今回、最初の私の仮説をそのまま支持しない記録が 2 つありました。

1 つ目は、導入例の **EABK 導入前** が、長い作業や再開依頼の多い期間だったことです。
フレームワークを外すだけで、依頼の範囲やモデルの問題が自動的に解決するわけではありません。

2 つ目は、非導入例の PRD が、後から加えた機能に追従していなかったことです。
動くものができても、変更の理由や要求との関係が自然に残るとは限りません。

反対に、導入例にも、Hooks の誤拒否による停止や、管理上の検査の誤検出がありました。
必要な確認を増やす仕組みが、実装を妨げることもあります。

**期待した改善と、新しく生じた負担の両方を記録しなければ、仕組みの価値は判断できません。**

### 6. 別の実験: 1 文で依頼できる変更を 6 件比べる

2 アプリの履歴には、対象や時期の違いがあります。
そこで、別に行った、同じアプリへの小さな変更の比較も確認しました。

**狙い** は、同じ 6 件の変更に対し、通常の Coding Agent と EABK の旧版を使った場合の結果と負担を見ることです。
実装側に見せない隠しテストを使い、各変更の合否を確かめています。

| 観点 | 導入例（EABK の旧版） | 非導入例（通常の Coding Agent、Claude Sonnet 5.5） |
|---|---:|---:|
| 出発点・依頼 | 同じアプリの 1 文で依頼できる変更 6 件 | 同じアプリの 1 文で依頼できる変更 6 件 |
| 変更 1 件あたりの平均時間 | 47.6 分 | 3.1 分 |

時間とクレジットだけを比べて、追加の確認に価値がなかったとは言えません。

## 考察

### 1. 条件と成果: 製品の機能があることと、同じ結果になることは別

GitHub の 2026 年 2 月 25 日の Copilot CLI 一般提供の案内には、Plan mode、Autopilot、並列の専門 Agent、Skills、Custom agents、Hooks などが記載されています [R1]。

つまり、少なくとも Copilot CLI には、HVE や旧版 EABK が利用・補強してきた機能の一部がありました。
EABK 自体も、Agent や Hooks などの仕組みの上に作られています。

ただし、**製品に部品が存在することと、独自の Workflow と同じ順序・制約・監査が実行されることは同じではありません。**
独自の仕組みが担っていたのは、単なる機能の代替だけでなく、作業手順の固定や、結果の記録でもあったと考えています。

GitHub は、Claude Opus 5.5 の案内で、従来モデルと同程度のタスク解決を、より少ないステップと Token で行い、複数ステップの作業でエラーから回復したと説明しています [R2]。
これは提供元による説明です。
今回の 2 アプリの差が、そのモデルの改善によって生じたことを直接証明するものではありません。

### 2. 所要時間と手戻り: オーケストレーションは必要な分から選ぶ

非導入例では、範囲を区切った依頼を重ね、再開の Prompt が記録されないまま最初のリリース版に到達しました。
別の 6 件の変更実験でも、通常の Coding Agent が隠しテストに全件合格しました。

私には、これは **すべての変更に旧版 EABK の工程を通す必要があるのか、見直す理由** に見えます。

一方で、導入例の導入前にも長い作業があり、導入後には依頼の形が変わりました。
そのため、「フレームワークを外せば短くなる」とまでは結論できません。
モデル、依頼、環境、アプリの範囲を分けた再実験が必要です。

### 3. 品質と要求の追跡: 正本と外部の判定を残す

PRD が更新されない問題は、非導入例でも実際に起きました。
また、小さな変更でも、既存のセキュリティ要求との衝突が隠れています。

私が当面残したいのは、次のような薄い規律です。

| 作業 | 当面の候補 | 任せきりにしない点 |
|---|---|---|
| 要求の管理 | PRD を正本とし、振る舞いを変える変更では同じ変更の中で更新する | PRD が最新か、要求の意味が正しいかを人が確認する |
| テスト | 要求と受入基準をテストからたどれるようにする | ID が書かれているだけで、要求を検証したことにはならない |
| 合否判定 | Agent の外でビルド・テスト・必要な機械検査を実行する | CI の設定、実行環境、対象範囲、結果を確認する |
| 要求の矛盾 | リリース前などの節目に、別の視点で要求と変更を監査する | 別の Agent やモデルを使うだけで、矛盾の検出は保証されない |
| 安全性・プライバシー | 既存の要求に触れる変更は、影響範囲を明示して判断する | 変更が短いという理由だけで確認を省かない |

これらを短い規則と CI で実現することは候補になります。
ただし、**今回、短い規則と CI だけで同じ品質が保てることを実証したわけではありません。**
チームの人数、変更の並行性、監査義務や失敗時の影響によっては、より強い仕組みが必要かもしれません。

### 4. 費用と運用負荷: モデルの使い分けは次に試す

非導入例の 28 件の Prompt を、報告書では次の 4 段に分類しています。

| 段階 | 件数 | 記録された区間長 | 今回の状態 |
|---|---:|---:|---|
| 調査 | 2 件 | 20.8 分 | 調査結果を次の PRD の入力にした |
| PRD | 1 件 | 9.6 分 | 要求 ID と受入基準を含む PRD を作った |
| 主実装 | 6 件 | 251.3 分 | PRD を基に実装し、検証を進めた |
| 小さな変更と関連応答 | 19 件 | 574.9 分 | 機能追加や修正を行ったが、PRD の追従に不足があった |

調査と PRD の区間長は合計 30.4 分で、全体 856.6 分の約 3.5% です。
ただし、短かったこと自体は、この 2 段階が手戻りを減らしたことの証明ではありません。

また、「小さな変更」は報告書上の分類です。
この 19 件には、複数カメラの同期のように、影響範囲が小さいとは限らない依頼や関連する応答も含まれます。

この段階の記録上の課金倍率の合計は 16,505 で、全体 20,889 の約 79% でした。
そのうち 16,425、約 99.5% が Claude Opus 5.5 に対応しています。

私は、主実装には高性能なモデルを使い、変更の範囲が狭く、既存の安全性要求に触れない場合には中規模モデルも試したいと考えています。
ただし、**非導入例では、この切り替えは実施されていません。**

たとえば、報告書の 1,175 呼び出しをすべて倍率 1 と仮定すると、この段階の代理指標は 16,505 から 1,175 となり、約 92.9% 減る計算です。
これは、呼び出し数が変わらず、すべてに同じ倍率を適用できるという仮定上の計算です。
品質、再試行、実際の請求額は検証していません。**【要確認：中規模モデルでの品質、手戻り、実請求額】**

報告書に載せた 4 段のサイクルの図を、ファイルパスだけ匿名化して掲載します。
これは実験結果ではなく、今後の進め方の **提案** です。

## 今回の結果から言えないこと

- **因果関係**: 2 アプリの時間差を、EABK の有無、モデルの進化、依頼の切り方のいずれか 1 つには帰属できません。
- **同等の完成度**: 要求の数は近くても、機能、設計、コード量、受入条件が異なります。最初のリリース版も外部の盲検受入を終えていません。
- **全期間の時間・費用**: 導入例には会話記録のない期間があり、後半の Token もありません。記録された時間には待機を含み、run とジョブの単位も異なります。
- **Lite の効果**: 導入例で使ったのは EABK 0.5.x です。Lite 0.6.0 を同じ対象・条件で比較した結果ではありません。
- **長期保守**: 非導入例の観察は 2 日間です。数週間後の仕様のずれ、運用の負担、利用者からの不具合は評価していません。
- **モデルの使い分け**: 中規模モデルに切り替えた場合の品質、再試行、実際の請求額は未測定です。
- **統計的な一般化**: アプリの比較は各 1 例、小さな変更の実験は 6 件です。有意差や、別の組織・技術スタックでの再現性は示していません。
- **第三者による再現**: 公開一次資料の機能説明は読者が確認できますが、アプリの会話と履歴は公開していません。この記事だけで独立した再集計はできません。

## ここまでの整理

### 良かった点

- 導入例と非導入例の差だけでなく、導入例の EABK 導入前後も確認できました。
- 非導入例は、調査から PRD、実装、後続の変更へ進み、最初のリリース版に到達しました。
- 6 件の小さな変更では、両方式とも隠しテストに合格しました。
- EABK は、要求の矛盾や既存の安全性要求との衝突を記録した例がありました。

### 注意したい点

- フレームワークを使わない導入前の期間にも、長い作業と再開依頼がありました。
- フレームワークを使わなかったアプリでも、PRD と後続の機能にずれが生じました。
- テスト合格、要求 ID の存在、要求の意味の検証、外部受入はそれぞれ別です。
- 旧版 EABK では、Hooks の誤拒否や実行環境の問題も記録されています。

### 今回の限界

- 2 アプリは機能、コード量、モデル、時期、実行環境がそろっていません。
- 待ち時間には不在や承認待ちが含まれ、記録のない期間もあります。
- EABK Lite と中規模モデルへの切り替えは、今回の条件では未検証です。
- 非公開の履歴に依存するため、独立した第三者による再現はまだありません。

## 次に確かめたいこと

次は、仕組みの是非を印象だけで決めず、同じ出発点で確かめたいと思います。

1. 同じアプリ、同じ要求、同じ初期状態から、フレームワークの有無とモデルをそれぞれ変え、条件を記録します。
2. 変更ごとに隠しテストを用意し、動作だけでなく、既存の要求との衝突と PRD の更新も確認します。
3. 時間はジョブの区間長と人の操作時間を分け、待機・再試行・実際の請求額を別々に記録します。
4. 判定役には方式を伏せ、可能なら私以外の人に採点と集計の再現を依頼します。
5. 短い規則と CI を使う条件では、一定期間の PRD 更新漏れと検査漏れも確認します。

この計画は **まだ実行していません**。
EABK の方が要求の矛盾を多く見つけ、追加の時間に見合う結果が出るなら、私の見方は修正する必要があります。
逆に、軽い規律で同じ品質を保てるなら、重い仕組みを外す根拠が強くなります。
