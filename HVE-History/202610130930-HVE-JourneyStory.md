## 3. ストーリー（章立て）

各章は「何をしたか → 何が起きたか → 失敗 → 発見 → 次への転換 → スライド化メモ」の順です。

### 第 0 章 出発点: 事業構想から始まった（01-23〜02）

**何をしたか（事実）**
- リポジトリー名が示すとおり、題材は会員・ポイント・特典などを扱う業務システム（Royalty Service の 2 世代目）です。
- 最初の仕事は、コードではなく **Future Scenario（未来シナリオ）の一覧 15〜20 件と、その詳細（FS01〜FS20）** でした。cloud agent に Issue / PR で書かせ、PM 系の Custom Agent の指示書を整備しました。
- 02 月には UC-10 の**ユースケース → ドメイン分析 → マイクロサービス抽出**へ進みました。

**何が起きたか（事実）**
- 1 つの成果物を「3 つのサブタスクに分割」し、各サブタスクを書いたあとに「Review Cycle 4 / 5 / 6」「3 回レビューで 105 件の問題を修正」と、人が決めた回数だけ自己レビューを回しました。commit の履歴にそのまま残っています。
- cloud agent の PR マージは 1 月 13 件、2 月 108 件、3 月 376 件と増えました。

**発見（推論）**
- この時期の分割とレビューの反復は、**当時のモデルの出力上限・精度・長文の一貫性を補うための手順**でした。その時点では合理的でした。
- そして、最初の題材が「事業構想」だったことは、のちの Business Envisioning への回帰として物語の伏線になります（第 9 章）。

**スライド化メモ**
- キーメッセージ: 「最初の依頼はコードではなく、事業の未来シナリオだった」
- ビジュアル: 1 月の commit ログの抜粋（"Create Future Scenario list with 20 prioritized scenarios"）と、2 月の "Review Cycle 4/5/6" の並び
- 実感を足す: `【実感を足す】` なぜ事業構想から始めたか

### 第 1 章 補助輪の時代: Best Practice で弱さを補う（02〜03 月）

**何をしたか（事実）**
- Custom Agent を 02-20 時点で 19 本。02-24 に複数の Workflow を単一の orchestrator に置換しました。
- 03-02 に「A-exec 分割」を強制する、DAG 風の実行フローを Agent の指示書に入れる、受入基準の検証セクションを入れるなどを実施しました。
- ファイル数は 02-20 時点 69 → 03-31 時点 754 と、約 1 か月で 11 倍になりました。

**何が起きたか（事実・推論）**
- 追加した手順は、どれも当時の弱さに対する**もっともな処方**でした。

| 当時の弱さ（推論） | 当時の処方 | 今どうなっているか |
|---|---|---|
| 1 回の出力が途中で切れる、長文の一貫性が崩れる | 成果物を 3 つのサブタスクに分割。「1 回の書き込みは 300 行以内」 | **今も有効。** 分割の 1 文（C1S）は Sonnet 5.5 でも成功率を 1/3 失敗 → 3/3 成功に変えた（EOS §3.3） |
| 1 回で品質が出ない | Review Cycle を固定回数。3 回レビュー | 敵対的レビューの量産へ（§第 4 章）。reviewer を外すと AI クレジットは約 26% 減り、結果は変わらなかった（3 方式比較 §5.6） |
| 途中で止まる、再開できない | Workflow の連続実行、Step 単位の resume、実行台帳 | Autopilot と再開で足りる（EOS §5.1 課題 1） |
| 大きな作業を分けて並列に流せない | DAG、Wave、ATG | `/fleet`、サブエージェントで足りる。ATG は品質が同じで時間 1.7〜2.25 倍・費用 2.49〜3.50 倍（EOS §3.1） |

**発見（推論）**
- ここで大事なのは、**「手順を足す」ことが、当時は正しい判断だったこと**です。この章を「失敗」とは呼びません。失敗は、**足した補助輪を外すタイミングを測る仕組みがなかったこと**にあります（第 4 章）。

**スライド化メモ**
- キーメッセージ: 「補助輪は、当時は正しかった」
- ビジュアル: 上の表（左: 当時の弱さ → 右: 今）。色分けで「今も有効 / 不要 / 逆効果」
- 実感を足す: `【実感を足す】` 当時、何に困って最初の手順を足したか

### 第 2 章 手順がフレームワークになる: HVE v1 の誕生と成長（03〜06 月）

**何をしたか（事実）**
- 03-18 に GitHub Copilot SDK のローカルオーケストレーター。03-31 に AQRC（QA 要求分類）Workflow。04-01 に Self-Improve ループ。04-21 に Work IQ の読み取り連携（QA / AKM / AQOD）。GUI、Fleet モード、Cloud Session を追加。
- 最終的な規模は、Workflow 13、Prompt 約 314 件、Skill 34 件、`knowledge/` に D01〜D21、`hve/` の Python 934 ファイル・約 27.7 万行です。
- 版は 06-09 の 0.1.1 から始まり、08-16 の 0.8.1 を経て、**10-03 の 0.8.197** に至りました。8 月 24 日〜9 月 21 日の 4 週間だけで、0.8.40 から 0.8.132 まで約 90 回の版上げです。

**何が起きたか（事実）**
- HVE は「業務要件の整理から設計・実装・検証までを、再現可能なワークフローとして運用する」ことを目的にしていました。
- 解こうとした課題は 10 個あり、あとの整理で次の 3 つに分類できました（EOS §5.1）。
  - 7 個: Copilot 本体の機能か運用の規則で足りる（**不要**）
  - 3 個: リポジトリーごとの小さな仕組みで足りる（**薄い仕組み**）。偽の PASS、要件索引、費用と証跡
  - **課題そのものは今も実在する。不要になったのは、解決のために Framework やアプリケーションを作り保守すること**

**失敗（事実）**
- HVE の開発・保守に **181,055 AIU（約 1,811 USD）**。その仕組みで作った業務アプリは未完成でした（第 5 章）。

**スライド化メモ**
- キーメッセージ: 「課題は本物だった。ただし、解き方（自作フレームワーク）は不要になった」
- ビジュアル: 10 個の課題 × 3 分類のマトリクス（EOS §5.1 の表を簡略化）
- 数字: 0.8.1 → 0.8.197 を 48 日、約 27.7 万行

### 第 3 章 Knowledge をつなぐ: Work IQ の最初の設計と、その誤算（04 月〜10-01）

これは仮説 H4 の中心です。

**何をしたか（事実）**
- 04-21 に Work IQ を、QA（事前の質問票）と知識化（AKM / AQOD）に**読み取り専用で**統合しました。
- 設計は「HVE が質問を最大 10 問に絞り、1 問につき 1 回だけ Work IQ に固定の形式で問い合わせる」。許可ツールは `ask` の 1 つ。応答は 1〜5 行の固定スキーマに押し込める、というものでした。

**何が起きたか（事実）**
- 実測では **35 クエリ中、見つかった 5 件（14%）、一部 4 件（11%）、見つからない 23 件（66%）、使えない 3 件（9%）** でした（2026-10-01 の調査。情報がテナントに存在しない可能性もあり、方式だけが原因とは断定していません）。
- 調査の結論: Copilot SDK は MCP ツールをモデルが自分で選んで呼ぶ。固定の 1 問 1 回の枠は、**モデルの調査能力を明らかに抑えていた**。Work IQ 自身が推奨する `retrieve` 優先の使い方もできなかった。
- 同日、Work IQ 専用処理を**汎用の「知識探索エージェント」1 セッション**に置き換える commit を行いました（10-01）。

**発見（事実・推論）**
- 「Work IQ のために専用の対話・分割・解析を作る」のではなく、「ツールを渡して、モデルに反復調査させる。人は読み取り専用・書き込み先の制限・出典の必須化・監査ログだけを決める」へ。
- ただし、**制約**も確かめました（事実）。Cloud の Coding Agent は OAuth を使うリモート MCP を未サポートで、Work IQ の自律調査が現実的に動くのは、**利用者のマシンで認証済みの Copilot CLI / SDK セッション**だけです。

**スライド化メモ**
- キーメッセージ: 「Knowledge 連携は、仕組みを作るより、モデルに道具を渡して任せる方が効く。ただし、認証という現実の壁は残る」
- ビジュアル: 左 = 旧設計（固定 1 問 1 回 → 66% NOT_FOUND）、右 = 新設計（探索エージェントが `retrieve` を反復）。下に「残る条件: ローカル認証済みセッション、機密区分」
- 注意: 「Coding Agent が適切にできるようになった」と断言せず、「設計としては任せる方向に変え、実行環境の条件付きで動く」と言う

### 第 5 章 測り始めた: 無駄に気づいたのは 8 か月後（09-18〜10-03）

**何をしたか（事実）**

**気づかなかった理由（推論）**
1. **長時間・大量 Token は、1 回の Prompt ごとには「いつものこと」に見える。** 総量を集計して初めて、少数の巨大セッションが支配的だと分かる。
2. **コストの記録がなかった。** セッション履歴は、VS Code Chat と cloud agent が集計に入らない、履歴の保持期間が短い（HubRadio と AutoVision は 09-21 以降、StudyReport-Evaluator は 09-24 以降しか残っていない）、PC 再起動で集計が失われる、など。③の開発では、PC 再起動で区間 1 の Token の実測値が消え、推定になりました。
3. **v2 でも、コストはまだ自動集計されていません（事実）。** BAS の実行履歴（`run-history.md`）は、直近 3 回の実行すべてで AI クレジットが「**未取得**」です。3 方式比較 §5.7 も「Token の集計はツールキットにない」と記しています。
4. 測り始めた 09-18 は、開始（01-23）から約 8 か月後です。`【要確認】` 記録に残る最初の測定が 09-18 であり、それ以前に別の測定がなかったとまでは断定できません。

**発見（事実）**
- 時間の大半は LLM の推論ではなく、**ツールの実行・承認待ち・直列実行・文脈の肥大**でした。外部のオーケストレーターが改善できるのは、その一部（直列実行）だけです。
- 「全部のタスクが長い」のではなく、**少数の巨大セッションが時間を食い尽くしていた**。

**スライド化メモ**
- キーメッセージ: 「無駄は、見えるようにしてはじめて無駄になる」
- ビジュアル: ①ヒストグラム（セッション所要時間の分布）、②「18.2% のセッションが 73.6% の時間」の円グラフ、③「測り始めた日」を年表に旗で立てる
- 実感を足す: `【実感を足す】` 集計結果を最初に見たときの感想

### 第 7 章 薄い足場を作り直す: ② new-era から ③ EABK（HVE v2）へ（10-06〜10-10）

**② new-era（10-06〜07）**（事実）
- Prompt 7 回・1 日・総待ち 7 時間 06 分・約 132 USD 相当で後継版を完成。前版は Prompt 254 回・32 日でした。

- P-FR（約 42 KB）の中身は、Anthropic の公式ガイドの作法（ターンの終え方、範囲、サブエージェントの使い方、テストを弱めない等）とほぼ同じ文でした。**HVE が数万行のコードで解こうとしたことの多くが、数段落の自然言語に置き換わっていた。**

**③ EABK（10-07 設計 → 10-08 実装・公開）**（事実）

- ユーザーは conductor に Prompt を **1 回**送るだけ。最大 24〜48 時間、人の介入なしに、要求定義 → 独立監査 → System Test の先行設計 → 並行実装 → 直列の統合 → 最終監査 → 報告まで進む。

**比較実験（10-08〜10-10）**（事実）

| 観点 | ⓪ 素の Coding Agent | ① 対話型 Vibe Coding | ② Prompt 駆動 | ③ EABK |
|---|---|---|---|---|
| 小さな変更（1 文で言える 6 件） | **隠しテスト 6/6。時間と費用は最小** | – | – | 6/6。⓪の約 15 倍の時間、約 31 倍の AI クレジット |
| 「止まる・繰り返す」 | 小: 問題なし／全体: 1 回では終わらない | **人の Prompt の約半分が再開、4 割強が打ち直し** | おおむね解決（人の Prompt 5〜7 回） | **解決**（人の Prompt 1 回で 71 分止まらず。完走の再計測は 5 回止まっても 1 文で再開） |

**失敗と発見（事実）**
- 失敗: EABK のモデル指定（作業役は安いモデル）は、15 回の実行のうち **5 回しか守られなかった**。範囲の黙った縮小。実行上限を実際より厳しく解釈して早めに止まる。再計測中に claude-opus-5.5 が CLI で使えなくなる。

- 発見: 「何もない⓪が一番よい」は、**小さな変更に限って正しい**。問題が起きるのは、⓪をアプリ全体に繰り返し使った（①）ときです。

**利害関係の明示（事実）**
- ③はあなたが開発したツールキットです。実験の設計・実行・集計と執筆は AI が行い、採点役にも同じ系統のモデル（Sonnet 5.5）を使いました。各条件の試行は 1〜6 回で、統計的な有意差は示せません。**スライドにもこの注記を残してください。**

### 第 8 章 同じ道具を Business に向ける: Business Analytics Studio（10-08〜10-13）

これが「個人の Vibe Coding を Business Envisioning まで拡大する」挑戦の現在地です。

**出発点の失敗（事実）**
- 元になったのは、法人顧客向けの ToBe 構想・意思決定支援のダッシュボードを**毎回ゼロから生成する Prompt**（ショー体験・ブランド演出を強化した版）です。
- 10-08 の実行結果を 10-09 に分析すると、次の 4 つの失敗が見つかりました。

| # | 失敗 | 根拠 |
|---|---|---|
| P-1 | 1 件あたり **60 分以上** | 調査 約 25 分以上（推定）、`npm install` 約 5 分、コード生成 約 11 分、検証 約 17 分 |
| P-2 | 時間をかけても要件の一部しか実装されない | インクキャンバス、PDF 出力、ナレッジグラフ、LOD、URL 状態復元、ホワイトボード、モックアプリ、アーキテクチャ図、`customer-research.md` が欠けていた |
| P-3 | 毎回生成するため、品質と見た目が安定しない | 生成のたびに実装が変わり、検証もやり直し |
| P-4 | 工程ごとの所要時間を測っていない | 改善の効果を定量評価できない |

**設計の転換（事実）**
- 目標を「**顧客 1 件あたり 3〜6 分で、全要件を満たすアプリを用意する**」に置き、仕組みを 3 つに分けました。

| 構成要素 | 内容 | 作る頻度 |
|---|---|---|
| A. 共通アプリ本体（雛形） | 全機能を実装したビルド済み Web アプリ。顧客固有の情報はコードに含めない | 1 回（以後は保守） |
| B. 顧客パック | 顧客ごとの調査結果・ブランド・サンプルデータ（JSON / Markdown / アセット） | 顧客ごと |
| C. 生成パイプライン（Copilot Skill） | 雛形の複製 → 事前調査の取り込み → データ生成 → 検証 → 起動 | 1 回（以後は保守） |

- これは**第 5 章の学び（毎回生成せず、再利用できるものはデータとして分ける）の Business 版**です。
- 実行は EABK（HVE v2）の `/build`。BAS は 10-08 20:51 に開始、10-09 に要求定義書の初版（FR-001〜131、NFR 24 件、AC 189 件）と System Test 台帳 121 ケース、土台（Vite + React + Fluent UI）まで進みました。

**現在の規模（事実。2026-10-13 時点）**

| 項目 | 値 |
|---|---|
| 期間・commit | 6 日・299 commit（10-09: 154、10-10: 87、10-12: 39、10-13: 18） |
| 要求 | FR 144 件、受入基準 236 件、NFR 28 件 |
| System Test | 台帳 141 ケース（E2E の採番は 221 まで） |
| 記録された実行（`run-history`） | 3 回: 1.7 時間、2.1 時間、1.0 時間。いずれも「全件完了」。AI クレジットは**未取得** |
| 利用者 | 事業部長・Product Manager・戦略コンサルタント |

**Business 固有の設計（事実）**
- **数値には出典（Work IQ / URL / 取得日）と確度（高・中・低・推定）を付けて、画面上で確認できる**（FR・AC-009）。
- **Work IQ 由来の情報には機密区分（internal / shareable）を持たせ、internal はエクスポート時に匿名化できる**（FR-117）。
- 顧客情報（顧客名・議論内容・顧客パック）は、既定でコミットしない。外部送信は Copilot SDK と設定した AI API に限る。
- Work IQ・LLM・音声・手書きは、使えない場合にモックで動く。実接続の確認は「manual（BLOCKED）」として残す。

**発見（推論）**
- Business Envisioning では、**コードではなく「顧客パック（データ）」が価値の中心**になります。これは次の章（H3 の「何を保持するか」）の答えの重要な一部です。
- 同時に、**v2 でも、Work IQ が認証で使えず「社内情報未確認」として進んだ**。Knowledge 連携は、設計の転換だけでは完結しません。

**スライド化メモ**
- キーメッセージ: 「コードの Vibe Coding で学んだ 3 つ（正本・決定的な検査・再利用できるものをデータに分ける）を、事業構想へ持ち込んだ」

## 5. 仮説の検証（詳細）

### 5.1 H1: 早期に取り組んだ人ほど、低性能な Model や Coding Agent を Best Practice で補っていたので、それが今ボトルネックになっている

**判定: 支持（強い）。ただし、言い直しを推奨します。**

| 区分 | 根拠 |
|---|---|
| 支持する事実 | ① 02 月の Review Cycle 固定回数、3 サブタスク分割。② 03 月の手順の量産（69 → 754 ファイル）。③ HVE v1 の規模（Prompt 約 314 件、Skill 34 件、約 27.7 万行）。④ ATG: 品質は同じで時間 1.7〜2.25 倍・費用 2.49〜3.50 倍。⑤ reviewer なしで −26%、監査なしで −50%（結果は同じか妥当）。⑥ new-era は HVE・ATG・Skill なしで完了。⑦ P-FR は公式ガイドの数段落と同じ内容で、HVE の機能の多くを置き換えた。⑧ Anthropic の見解: harness の各部品は、モデルが自力でできないことについての仮定であり、モデルが良くなると古くなる |
| 反する／留保する事実 | ① new-era は前版のコードと要求の 92% を引き継いでおり、モデルの差だけでは説明できない。② 「分割の 1 文」「外部の決定的ゲート」「要求の正本」は今も効く。③ HVE の業務アプリが完成しなかったのは、規模の差もある。④ n=1。同じ人・同じモデル・同じ時期の比較ではない |
| 推論 | **足かせになったのは「モデルの能力不足を前提にした足場」。「モデルの能力に依存しない足場」は、モデルが強くなっても残る**（Anthropic の「harness の組み合わせの余地は縮まず、移動する」と同じ結論）。 |

**推奨する言い方（スライド用）**
> 「早期に始めた人ほど、当時のモデルの弱さを補うために足場を積んだ。モデルが強くなっても、その足場は自動では消えない。足場には『能力不足を補うもの』と『能力に関係なく必要なもの』があり、前者を見分けて外すことが、今のボトルネック解消になる」

**この仮説をさらに確かめる方法（未検証）**
- 同じ 1 つの要求定義を、HVE v1 の Workflow と ⓪（最新モデル）で作り、時間・費用・受入基準の充足を比べる（比較レポートの E-6 に近い）。
- P-FR・conductor の節を 1 つずつ外して測る（PoC 分析 I4）。

### 5.2 H2: 実行時間と Token 消費量が無駄だったことに気づかない

**判定: 支持。**

- 事実: 8 時間超のセッション 18.2% が総時間の 73.6%、100k トークン超の呼び出しが LLM 遅延の 83.2%、最長ステップの 91.8% は LLM 以外の時間（第 5 章）。
- 事実: 記録に残る最初の本格的な測定は 09-18。履歴の保持は 09-21 以降（一部 09-24 以降）。
- 事実: ① の「止まったジョブの再開・エラー対処」が人の入力の約半分。**Token や時間の無駄は、コストというより「人の注意」に変換されていた。**
- 事実: v2 でも AI クレジットは自動集計されない（BAS の `run-history` は 3 件とも「未取得」）。
- 推論: 気づかない理由は、(1) 1 回ごとには見えない、(2) 測る仕組みがない、(3) 長く動くこと自体が「頑張っている」ように見える、の 3 つ。`【実感を足す】` (3) は私の推測です。
- 追加の留意: new-era では、入力の 96.4% がキャッシュ読込で、実際の新規入力は小さい。Token の総数だけでは費用の実態を表さない。**AIU（AI クレジット）、キャッシュの内訳、サブエージェント別、LLM 以外の時間の 4 つで見る必要がある。**

### 5.3 H3: 何のデータを保持して Vibe Coding を行えばよいのかは調査中

**判定: 現状の理解として妥当。有力な候補は挙げられるが、結論ではない。**

| データ | 目的 | 現在の扱い | 状態 |
|---|---|---|---|
| **要求定義書**（FR・NFR・AC・Q・PARAM） | 唯一の正本。矛盾・ドリフトを防ぐ | 書き手は 1 つ（hook で強制）。ID は決定的スクリプトで採番。150 件超で業務の境界ごとに分割 | 有力・採用済み |
| **カタログ**（要求 ID → 実装 → テスト → API・共通部品） | 重複実装・無駄な探索を減らす | 短い対応表 + `mdq` / `cq` の索引 | 有力。大規模化の限界は未検証 |
| **ID 台帳** | 並行作業での ID の重複を防ぐ | `id-registry`（BAS では約 88 KB） | 採用済み |
| **System Test の台帳**（受入基準から作る） | 実装ではなく要求からテストを決める | JSON の台帳。canary、増分実行 | 有力 |
| **run の状態**（`queue`・`progress`・結果・監査・証跡） | 中断からの再開、証跡 | `/work`（一時）に置き、最後に `/docs` と台帳へ転記 | 有力。「どこまで転記するか」は調整中 |
| **実行履歴**（`run-history`） | KPI の追跡 | 1 run 1 行 | **AI クレジットが未取得（課題）** |
| **Copilot セッションログ**（`events.jsonl` など） | 時間・Token・モデル・Prompt の実測 | 履歴は保持期間が短く、入口（VS Code / CLI / cloud）ごとに別。PC 再起動で集計が消える | **最大の空白** |
| **顧客パック**（Business 用） | 顧客固有のデータをコードから分ける | `public/data/*.json` など。出典・確度・機密区分つき | BAS で採用。スキーマは検証中 |
| **調査キャッシュと出典** | 事前調査の再利用、数値の根拠 | 有効期限つき（FR-123）、コミットしない | BAS で採用 |
| **判断・承認の記録**（質問票・承認・包括承認） | 自動化バイアスの抑制 | すべて「推奨どおり」「承認」になりがち（②で 9 件・10 件） | **未解決**（I6: 重要度で分ける案） |

**未解決の問い（スライドの「次の課題」に使えます）**
1. 要求・catalog・台帳は、どの規模（要求 150 件、300 KB 以上）で分割・索引化すべきか。
2. run の一時データのうち、永続させるものの基準は何か。
3. Token・時間・AI クレジットを、入口をまたいで 1 つの形式で残すには。
4. Business Envisioning で、出典・確度・機密区分をどの粒度で持つか。顧客パックのスキーマは、案件を重ねても安定するか。
5. 承認や判断の根拠を、「形だけの承認」にしない形で残すには。

### 5.4 H4: Knowledge（Work IQ など）との連携を Coding Agent が適切に行えるようになった

**判定: 部分的に支持。「任せる設計に変えた」は事実。「適切に行えるようになった」は、環境の条件つき。**

| 区分 | 根拠 |
|---|---|
| 支持する事実 | ① SDK はモデルに MCP ツールを見せ、呼ぶかどうかはモデルが決める。② 旧設計（固定 1 問 1 回）は 35 件中 66% が見つからず、`retrieve` も使えなかった（モデルの調査能力を抑えていた）。③ 10-01 に知識探索エージェントへ置換。④ new-era は Work IQ を 1 回使い、社内情報を検索した。⑤ EABK のユーザーガイドは、利用者が設定した Work IQ・Microsoft Learn・Azure などの MCP・plugin・skill を、conductor と作業役がそのまま使えるとしている |
| 反する／留保する事実 | ① Cloud の Coding Agent は OAuth を使うリモート MCP を未サポート。Work IQ の自律調査は、ローカルで認証済みのセッションに限られる。② BAS の自動実行で Work IQ は認証が必要で検索できず「社内情報未確認」。③ 10 月の Work IQ 呼び出し 3 件は成功なし（セッション履歴）。④ 旧設計の 66% は、情報がテナントに存在しない可能性もあり、方式だけが原因とは断定していない。⑤ 新設計（探索エージェント）の成功率は、まだ測っていない |
| 推論 | Coding Agent は Knowledge を「使う」能力は十分になったが、**認証・権限・機密という運用の壁が、成功を左右している**。Business Envisioning では、Work IQ が使えない場合の代替（Web → サンプル）と、機密区分・匿名化を最初から設計に入れる必要がある |
| 未検証 | 探索エージェント方式で、同じ 35 問を再実行したときの FOUND 率。`retrieve` 優先に変えた効果 |

**推奨する言い方（スライド用）**
> 「Knowledge への問い合わせは、仕組みで制御せず、モデルに道具を渡して反復させる方が良い。残る課題はモデルではなく、認証と権限と機密である」
